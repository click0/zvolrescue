# zvolrescue — Технічне завдання (ТЗ)

**Статус:** чернетка v0.1 · **Дата:** 2026-09-06 · **Власник:** Владислав В. Продан
**English version:** [SPEC.md](SPEC.md)

Це базове ТЗ на `zvolrescue` — відкриту утиліту для forensic-аналізу та
відновлення даних ZFS. Документ визначає проблему, межі проєкту,
функціональні та нефункціональні вимоги, CLI, архітектуру, етапи
поставки та критерії приймання. До першого тегованого релізу все тут —
пропозиція; правте вільно.

---

## 1. Призначення

У ZFS немає `undelete`. Після знищення dataset/zvol або коли пул не
імпортується після апаратного збою, варіанти сьогодні такі:

| Варіант | Проблема |
|---|---|
| `zpool import -F` / `-T <txg>` | Відкат **усього пулу**, чіпає пул, працює лише поки живі старі uberblock-и (кілька TXG / хвилин). |
| `zdb` | Інструмент налагодження, а не відновлення: нема робочого процесу витягання даних, падає на пошкоджених метаданих. |
| Скрипти типу `zfs_revert` | Перезаписують uberblock-и **на місці** на живих пристроях — деструктивно, лише один диск, без перевірки контрольних сум. |
| Комерційні (Klennet ZFS Recovery, UFS Explorer, ReclaiMe) | Закритий код, лише Windows, дорого, неможливо аудитувати для forensic chain of custody. |

`zvolrescue` закриває цю прогалину: **read-only, userland, аудитований**
інструмент, що читає on-disk структури ZFS напряму, реконструює
dataset-и — з основним фокусом на **zvol** (диски bhyve/VM, iSCSI-таргети,
томи контейнерів `crate`) — на будь-якому TXG, який ще є на диску, і
витягає їх у звичайні образи з перевірюваними контрольними сумами.

## 2. Терміни

| Термін | Значення |
|---|---|
| **zvol** | Том ZFS: dataset, представлений як блоковий пристрій (`/dev/zvol/<pool>/<name>`). |
| **TXG** | Transaction group; кожна on-disk зміна позначена TXG, у якому народилась. |
| **Uberblock** | Кореневий вказівник пулу для конкретного TXG; у кожній мітці зберігається кільце зі 128 штук. |
| **Мітка (label)** | Структура 256 KiB, 4 копії на vdev (2 спереду, 2 ззаду), містить nvlist-конфіг і кільце uberblock-ів. |
| **MOS** | Meta Object Set: загальнопуловий набір об'єктів, що описує всі dataset-и. |
| **Block pointer (blkptr)** | 128-байтова структура з до 3 DVA-копій блоку плюс метадані checksum/compression. |
| **Carving** | Відновлення даних скануванням сирого простору на впізнавані структури, а не за живими вказівниками. |
| **Evidence (доказ)** | Будь-який вхідний пристрій чи образ; інструмент ніколи не повинен його змінювати. |

## 3. Межі проєкту

### 3.1 Входить

* Читання пулів ZFS **без імпорту** в ядро.
* Пули в будь-якому стані: здорові, degraded, faulted, знищені (`zpool destroy`), з пошкодженими мітками/uberblock-ами, з відсутніми vdev, якщо надлишковість ще дозволяє реконструкцію.
* Відновлення **zvol** (основне) та **файлових dataset-ів** (другорядне: спочатку як сирі дампи об'єктів, пізніше — на рівні файлів).
* Робота з фізичними пристроями, розділами та файлами образів (`dd`, `.img`, sparse), включно з образами *окремих* членів vdev, зібраними у віртуальний пул.
* Forensic-огляд: часова шкала TXG, історія міток/uberblock-ів, історія створення/знищення dataset-ів, поблочна перевірка контрольних сум.

### 3.2 Не входить (v1)

* Запис у пул чи ремонт на місці. `zvolrescue` **ніколи не пише в evidence.**
* Монтування відновлених ФС (використовуйте `mdconfig(8)`/`losetup(8)` на витягнутому образі).
* Відновлення пулів, ключі шифрування яких недоступні (шифровані дані витягаються як ciphertext + метадані).
* GUI. TUI можливий пізніше (див. §10).
* Генерація потоків `zfs send` (можливо в пізніших етапах).

## 4. Користувачі та сценарії

| ID | Актор | Сценарій |
|---|---|---|
| UC-1 | Сисадмін | Виконав `zfs destroy pool/vm/disk0` не на тому хості. Потрібен zvol як образ протягом годин, поки вільні блоки не перевикористано. |
| UC-2 | Сисадмін | Пул не імпортується після відмови контролера (`zpool import` → "I/O error" / "corrupted data"). Треба врятувати диски VM з уцілілих vdev. |
| UC-3 | Forensic-аналітик | Отримав набір образів дисків із сервера ZFS. Має перелічити всі dataset-и, що існували в збереженому вікні TXG, коли їх створено/знищено, і витягти конкретні zvol із хеш-верифікованим chain of custody. |
| UC-4 | Сисадмін | Гостьова ФС усередині zvol зіпсувалась у момент T. Потрібен zvol *таким, яким він був* на попередньому TXG, хоча знімка нема. |
| UC-5 | Оператор хостів `crate` / bhyve | Масово експортувати всі zvol під деревом dataset-ів з офлайн-пулу на інше сховище для міграції чи аудиту. |
| UC-6 | Розробник / QA | Перевірити, що on-disk структури тестового пулу консистентні (кожен blkptr сходиться за checksum) після fault-injection прогону. |

## 6. Нефункціональні вимоги

| ID | Вимога |
|---|---|
| N-01 | **Read-only за побудовою.** Evidence відкривається `O_RDONLY`; немає шляху коду, який відкриває вхід на запис. Вихідні шляхи відхиляються, якщо вони резолвляться на вхідний пристрій. |
| N-02 | **Без залежності від ядрового ZFS.** Працює на хості без завантаженого модуля ZFS і ніколи не викликає `zpool`/`zfs`. |
| N-03 | **Масштабується до пулів у багато TB.** Потокове витягання з обмеженою пам'яттю (ціль: ≤ 512 MiB RSS незалежно від розміру пулу, без опційних кешів). |
| N-04 | **Fail soft.** Пошкоджені метадані дають попередження і частковий результат, ніколи не crash; кожне переривання має чітку причину та код виходу. |
| N-05 | **Відтворюваність.** Однакові входи + однакові аргументи → побайтово однакові виходи та звіти (timestamp-и лише у визначених полях). |
| N-06 | **Портативність.** FreeBSD 13.x–15.x — першого класу; Linux (glibc/musl) збирається і проходить тести; macOS — best-effort. |
| N-07 | **Аудитованість.** Малий набір залежностей, без мережі, детерміновані збірки, підписані релізні архіви. |
| N-08 | **Продуктивність.** Послідовне витягання zvol ≥ 70 % від сирої швидкості читання пристрою на mirror; ≥ 40 % на RAIDZ2 (один потік), з опційним пулом воркерів для паралельних checksum/decompression. |
| N-09 | **Локалізація.** Рядки UI — англійською; документація ведеться англійською та українською. |

## 7. CLI (пропозиція)

```
zvolrescue [глобальні опції] <команда> [опції] [аргументи]

Глобальні:
  -f, --format text|json      формат виводу (типово: text)
  -v, --verbose               можна повторювати
  -q, --quiet
      --evidence-log FILE     дописувати JSON Lines лог evidence
      --no-color

Команди:
  scan      DEV...                     виявити мітки ZFS на пристроях/образах
  labels    DEV [--all]                дамп nvlist міток (найкраща копія або всі 4)
  uberblocks DEV|POOL [--all]          кільце uberblock-ів з валідністю
  pool      POOLSPEC                   зведення зібраного пулу та його стан
  list      POOLSPEC [--txg N|--before TS] [--diff TXG2] [-r]
                                       dataset-и/zvol/знімки на TXG
  timeline  POOLSPEC                   TXG ↔ час ↔ події dataset-ів
  dump      POOLSPEC DATASET -o OUT.img [--txg N] [--strict] [--key KEYSPEC]
                                       витягти zvol (або дамп об'єктів ФС)
  carve     POOLSPEC [--type zvol] [-o DIR]
                                       знайти й реконструювати від'єднані dataset-и
  verify    POOLSPEC DATASET [--txg N] перевірити checksum кожного blkptr, без виводу даних
  report    POOLSPEC -o report.json    зведений forensic-звіт

POOLSPEC:  один або більше членів vdev, напр.
           /dev/ada0p3 /dev/ada1p3
           --image disk0.img --image disk1.img
           --pool-guid 0x1234…  (вибір серед кількох знайдених пулів)
KEYSPEC:   raw:FILE | hex:HEX | passphrase:FILE | prompt
```

Коди виходу: `0` успіх, `1` помилка використання, `2` evidence нечитабельний,
`3` пул не відновлюваний на запитаному TXG, `4` витягання завершено з
помилками (лише `--strict`), `5` відмова (записало б в evidence).

Приклад (UC-1):

```sh
# 1. Що на цих дисках і які TXG ще доступні?
zvolrescue scan /dev/ada0p3 /dev/ada1p3
zvolrescue uberblocks /dev/ada0p3

# 2. Коли зник pool/vm/disk0?
zvolrescue timeline /dev/ada0p3 /dev/ada1p3 | grep disk0

# 3. Витягти його з останнього TXG, де він ще був, з перевіркою checksum.
zvolrescue dump /dev/ada0p3 /dev/ada1p3 pool/vm/disk0 --txg 4816230 \
    --strict -o /mnt/rescue/disk0.img --evidence-log case42.jsonl
```

## 8. Архітектура

### 8.1 Мова та залежності

* **C++17**, той самий toolchain і CI-конвенції, що в [`crate`](https://github.com/click0/crate) (clang у базі FreeBSD, GCC/clang на Linux). Обґрунтування: продуктивність для потокової обробки багатьох TB, пряме використання C-заголовків ZFS, жодного runtime, який треба тягти на rescue-систему.
* Стиснення: `liblz4`, `libzstd`, `zlib`; `lzjb` та `zle` реалізовані наново (тривіальні).
* Checksum-и: `fletcher2/4` наново; `sha256/512` через OpenSSL/LibreSSL; `skein`, `edonr`, `blake3` вендоряться з OpenZFS (CDDL) у `third_party/`, ізольовано, щоб ядро під BSD-3 лишалось чистим.
* Шифрування: OpenSSL `EVP` (AES-CCM/GCM), деривація ключів OpenZFS (PBKDF2) наново.
* CLI: без фреймворків, лише `getopt_long(3)`; JSON через single-header бібліотеку.
* Опційний прапорець збірки `--with-libzpool` для перехресної перевірки з userland OpenZFS (`zdb`) у тестах. Не є runtime-залежністю.

### 8.2 Шари

```
cli/            розбір команд, форматування виводу, лог evidence
lib/
  io/           read-only доступ до пристроїв/образів, sparse-запис, таблиці розділів
  vdev/         розбір міток, дерево vdev, реконструкція mirror/RAIDZ/dRAID
  zio/          blkptr, резолв DVA, checksum-и, декомпресія, розшифрування
  dmu/          objset-и, dnode-и, обхід indirect-блоків
  dsl/          MOS, DSL dirs/datasets, знімки, вибір TXG, diff dataset-ів
  zvol/         витягання zvol, виявлення дірок, продовження
  zpl/          (пізніше) файлове відновлення ZPL
  carve/        сире сканування та оцінка кандидатів
  report/       модель звіту JSON/text
third_party/    вендорений CDDL-код (skein, edonr, blake3), ізольовано
tests/          unit-тести + інтеграційні тести на fixture-пулах
docs/           SPEC.md, SPEC.uk.md, research/, нотатки дизайну
```

Кожен шар вище `io/` — чистий: приймає інтерфейс `BlockSource` і ніколи не
торкається ОС, тому reader тривіально тестується на fixture-ах і портативний.

### 8.3 Інваріанти безпеки

1. Є рівно одна функція, що відкриває evidence, і в ній зашито `O_RDONLY` (плюс `O_EXCL` на платформах, які поважають його для блокових пристроїв).
2. Вихідні шляхи канонізуються і порівнюються з `st_dev/st_ino` кожного входу; збіг → переривання з кодом 5.
3. Жодних `system()`, викликів shell, мережевих сокетів (перевіряється тестом, що grep-ає імпорти бінарника).

## 9. Стратегія тестування

* **Unit-тести** для кожного парсера on-disk структур на «золотих» байтових масивах із реальних пулів.
* **Fixture-пули**, що генеруються в CI на FreeBSD-runner-і (див. [freebsd-runner-setup](https://github.com/click0/crate/blob/main/docs/freebsd-runner-setup.md) у `crate`) та на Linux з OpenZFS:
  * топології: single, mirror-2, raidz1-3, raidz2-4, raidz3-5, draid1;
  * dataset-и: zvol з відомим псевдовипадковим вмістом у кожній комбінації compression/checksum, sparse-zvol, шифровані zvol, дедупліковані zvol, знімки та клони;
  * сценарії: `zfs destroy` → відновлення на старішому TXG; `zpool destroy` → відновлення; один член відсутній; в одного члена занулені мітки; випадкове пошкодження 1 MiB у даних; випадкове пошкодження в метаданих.
  * перевірка: SHA-256 витягнутого образу дорівнює SHA-256, записаному до знищення.
* **Перехресна перевірка**: на хостах з userland OpenZFS порівнювати вивід `zvolrescue list`/`uberblocks` із `zdb -l`/`zdb -u`/`zdb -d`.
* **Fuzzing**: libFuzzer-харнеси для парсерів nvlist, blkptr, dnode і ZAP.
* **Статичний аналіз**: `-Wall -Wextra -Werror`, clang-tidy, job з ASan/UBSan.

## 11. Ризики та пом'якшення

| Ризик | Пом'якшення |
|---|---|
| Деталі on-disk формату недодокументовані; єдине джерело істини — код OpenZFS. | Вести `docs/research/ondisk-notes.md` з посиланнями на рядки коду OpenZFS для кожної структури; перехресна перевірка з `zdb` у CI. |
| Feature flags еволюціонують (нове стиснення, `raidz_expansion`, `blake3`). | Матриця feature flags у виводі `list`/`pool`; коректна відмова на невідомих *read-incompatible* фічах, попередження на невідомих read-compatible. |
| Вендоринг CDDL-коду проти ліцензії BSD-3. | Ізолювати в `third_party/` з окремим файлом ліцензії; ядро вільне від нього; задокументувати в `LICENSE.third_party`. |
| Вікно відновлення коротке (звільнені блоки перевикористовуються). | На першій сторінці документації: *негайно припиніть запис у пул, експортуйте його, зніміть образи дисків*. `scan` одразу друкує вік найстарішого придатного uberblock-а. |
| Користувачі очікують ремонту на місці. | Назва інструмента, README та `--help` чітко кажуть, що він ніколи не пише в пул; для цього — `zpool import -F/-T`. |

## 12. Відкриті питання

1. Чи етап 1 робити лише під FreeBSD, щоб рухатись швидше, а Linux CI додати на етапі 2? (Пропозиція: Linux CI з етапу 0 — генерація fixture там простіша, і код лишається портативним з першого дня.)
2. Розширення RAIDZ (`raidz_expansion`) — reflowed-розкладки: підтримати на етапі 2 чи відкласти?
3. Вендорити `skein/edonr/blake3` чи залежати від зовнішньої бібліотеки — вирішити на старті етапу 2.
4. Назва бібліотечного target-у: `libzvolrescue` чи `libzfsread`? Друга чесніша щодо обсягу, якщо файлове відновлення таки з'явиться.
