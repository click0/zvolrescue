# zvolrescue — Технічне завдання (ТЗ)

**Статус:** живий документ, переглянуто 2026-09-10 (інструмент на v0.2.0) · **Власник:** Владислав В. Продан

**English version:** [SPEC.md](SPEC.md) · **Супутні інструменти:** [COMPANIONS.uk.md](COMPANIONS.uk.md)

Це базове ТЗ на `zvolrescue` — відкриту утиліту для forensic-аналізу та
відновлення даних ZFS. Документ визначає проблему, межі проєкту,
функціональні та нефункціональні вимоги, CLI, архітектуру, етапи
поставки та критерії приймання. До першого тегованого релізу все тут —
пропозиція; правте вільно.

---

## 1. Призначення

У ZFS немає `undelete`. Після знищення dataset/zvol або коли пул не
імпортується після апаратного збою, варіанти сьогодні такі:

| Варіант | Проблема |
|---|---|
| `zpool import -F` / `-T <txg>` | Відкат **усього пулу**, чіпає пул, працює лише поки живі старі uberblock-и (кілька TXG / хвилин). |
| `zdb` | Інструмент налагодження, а не відновлення: нема робочого процесу витягання даних, падає на пошкоджених метаданих. |
| Скрипти типу `zfs_revert` | Перезаписують uberblock-и **на місці** на живих пристроях — деструктивно, лише один диск, без перевірки контрольних сум. |
| Комерційні (Klennet ZFS Recovery, UFS Explorer, ReclaiMe) | Закритий код, лише Windows, дорого, неможливо аудитувати для forensic chain of custody. |

`zvolrescue` закриває цю прогалину: **read-only, userland, аудитований**
інструмент, що читає on-disk структури ZFS напряму, реконструює
dataset-и — з основним фокусом на **zvol** (диски bhyve/VM, iSCSI-таргети,
томи контейнерів) — на будь-якому TXG, який ще є на диску, і
витягає їх у звичайні образи з перевірюваними контрольними сумами.

## 2. Терміни

| Термін | Значення |
|---|---|
| **zvol** | Том ZFS: dataset, представлений як блоковий пристрій (`/dev/zvol/<pool>/<name>`). |
| **TXG** | Transaction group; кожна on-disk зміна позначена TXG, у якому народилась. |
| **Uberblock** | Кореневий вказівник пулу для конкретного TXG; у кожній мітці зберігається кільце зі 128 штук. |
| **Мітка (label)** | Структура 256 KiB, 4 копії на vdev (2 спереду, 2 ззаду), містить nvlist-конфіг і кільце uberblock-ів. |
| **MOS** | Meta Object Set: загальнопуловий набір об'єктів, що описує всі dataset-и. |
| **Block pointer (blkptr)** | 128-байтова структура з до 3 DVA-копій блоку плюс метадані checksum/compression. |
| **Carving** | Відновлення даних скануванням сирого простору на впізнавані структури, а не за живими вказівниками. |
| **Evidence (доказ)** | Будь-який вхідний пристрій чи образ; інструмент ніколи не повинен його змінювати. |

## 3. Межі проєкту

### 3.0 Принцип дизайну: одна атомарна утиліта

`zvolrescue` — інструмент одного призначення, а не платформа. Цей принцип
обов'язковий для кожного наступного рішення в документі:

* **Одна робота.** Взяти on-disk структури ZFS з набору пристроїв чи
  образів і видати звичайний образ одного dataset-у (насамперед zvol).
  Виявлення (`scan`) і вибір (`list`) існують лише тому, що ця робота їх
  потребує.
* **Один статичний бінарник.** Без конфігураційних файлів, демона, плагінів,
  читання оточення, мережі, викликів shell. Усе, що потрібно для запуску, —
  у командному рядку та на evidence.
* **Чисті запуски.** Однакові аргументи над однаковим evidence дають
  побайтово однаковий вихід і однаковий JSON. Між запусками нічого не
  кешується.
* **Компонується, а не охоплює все.** Текст для людей, JSON для машин,
  образи у файли. Усе, що не потрібне, щоб дістати dataset — forensic-часові
  шкали, carving від'єднаних даних, зведені звіти, файлове відновлення — це
  *супутній інструмент* (§7.1), який використовує ті самі бібліотеки, а не
  новий режим основного бінарника.

### 3.1 Входить

* Читання пулів ZFS **без імпорту** в ядро.
* Пули в будь-якому стані: здорові, degraded, faulted, знищені (`zpool destroy`), з пошкодженими мітками/uberblock-ами, з відсутніми vdev, якщо надлишковість ще дозволяє реконструкцію.
* Відновлення **zvol** (основне) та **файлових dataset-ів** (другорядне: спочатку як сирі дампи об'єктів, пізніше — на рівні файлів).
* Робота з фізичними пристроями, розділами та файлами образів (`dd`, `.img`, sparse), включно з образами *окремих* членів vdev, зібраними у віртуальний пул.
* Forensic-огляд: часова шкала TXG, історія міток/uberblock-ів, історія створення/знищення dataset-ів, поблочна перевірка контрольних сум.

### 3.2 Не входить (v1)

* Запис у пул чи ремонт на місці. `zvolrescue` **ніколи не пише в evidence.**
* Монтування відновлених ФС (використовуйте `mdconfig(8)`/`losetup(8)` на витягнутому образі).
* Відновлення пулів, ключі шифрування яких недоступні (шифровані дані витягаються як ciphertext + метадані).
* GUI. TUI можливий пізніше (див. §10).
* Генерація потоків `zfs send` (можливо в пізніших етапах).

### 5.6 Відновлення нульової точки vdev, коли міток нема

Кожен DVA у пулі відносний: *фізична адреса = початок vdev + 4 MiB (дві
передні мітки і boot-зона) + offset*. Коли всі чотири мітки члена
перезаписано — і `vdev_phys`, і кільця uberblock-ів — разом з ними зникають
три речі: базис («нульова точка»), геометрія (`ashift`, діти та їхній
порядок, id top-level vdev-а) і кореневий вказівник. Інструмент має
розглядати їх як три окремі відновлення, а базис ніколи не *припускати*:
він приймається лише після криптографічної перевірки об on-disk вміст.

Якорі для базису, від дешевих до дорогих; кожен наступний потрібен лише
тоді, коли попередні недоступні:

| ID | Прі | Вимога |
|---|---|---|
| F-60 | S | **Таблиці розділів** (F-06): первинна і резервна GPT, MBR, а також конвенції розмітки (вирівнювання 1 MiB; хвостовий `-part9` на 8 MiB у Linux при whole-disk; порядок `freebsd-boot`/swap/`freebsd-zfs` у FreeBSD) дають *кандидатів* на базис, ніколи не базис. |
| F-61 | S | **Будь-який вцілілий uberblock** (F-05): кожен uberblock несе вбудовану контрольну суму `ZIO_CHECKSUM_LABEL`, верифікатор якої — його власний vdev-відносний зсув. Uberblock, знайдений за магією на фізичній позиції `P`, підтверджує базис `B` тоді й лише тоді, коли сума сходиться з верифікатором `P − B`; один збіг фіксує базис точно, каже, до якої з міток L0–L3 належав слот, і так відновлює старий розмір vdev навіть після перестворення розділу з іншим розміром. Працює при всіх чотирьох затертих `vdev_phys`, аби вижив хоч один слот кільця. |
| F-62 | S | **Мітки сусідів**: у дзеркалі чи RAIDZ конфіги інших членів дають `guid`, `asize` і `ashift` втраченого; `asize` плюс вирівнювання лишає жменю кандидатів, які підтверджуються F-61/F-63. |
| F-63 | C ◇ | **Самоузгодженість вказівників, повністю автоматично** (найгірший випадок: усі кільця втрачено і підказок нема): сканувати структури, впізнавані без базису (dnode-масиви — тип ≤ 54, `indblkshift` 9..17, малі `nlevels`/`nblkptr`, 512-байтний період; непрямі блоки; objset-заголовки), зібрати з них вказівники і підтвердити кандидата `B` тим, що блок за адресою `B + 4 MiB + offset` має контрольну суму з вказівника. Кандидати перебираються з кроком `1 << ashift` (сам `ashift` випливає з найменшого кроку зсувів DVA і гранулярності `asize`) у вікні вирівнювання. Хибний базис не проходить жодної перевірки, правильний проходить усі. Gang-заголовки (верифікатор `[vdev, offset, birth]`) і ланцюжки ZIL (`zc_next_blk` проти фізичної позиції наступного блока) — додаткові якорі. |
| F-64 | S ◇ | **Корінь без uberblock-ів**: коли базис відомий, а жоден uberblock не вижив, знайти MOS скануванням кандидатів `objset_phys` типу META, ранжувати їх за найвищим `birth` у вказівниках і за повнотою обходу MOS, далі йти DSL як звичайно. Це територія `zvolcarve` (F-41/F-42), не атомарного бінарника. |

**Що вже реалізовано.** Найдешевший якір F-60 на місці: коли дано образ
цілого диска, читається GPT (основна чи резервна, з секторами 512 або
4096) або MBR, позначаються ZFS-типи розділів, і початок кожного розділу
стає кандидатом бази — прийнятим лише там, де сходиться контрольна сума
мітки, бо переписана таблиця і є одним зі способів, якими пул перестає
імпортуватися. Використовується і *довжина* розділу: задня пара міток
лежить відносно власного розміру vdev, тож член, прочитаний до кінця
диска замість кінця свого розділу, знаходить дві мітки з чотирьох. Це
F-06 у тому обсязі, який потрібен атомарному бінарнику. F-61 є в
інструменті: `scan` шукає в члені магію
uberblock-а, підтверджує кожне влучання його ж вбудованою контрольною
сумою і повідомляє кожен базис, що підтвердився, — з кількістю
підтверджень, мітками, з яких вони походять, діапазоном TXG і розміром
vdev, який випливає з влучання в задню мітку. Пошук запускається сам на
члені без жодної читабельної конфігурації міток і на вимогу —
`--zero-point` (`--zero-point-whole`, `--psize BYTES`). Передня пара
міток не потребує жодної гіпотези; задня розміщена відносно розміру
vdev, тож підтверджує базис лише разом із ним. Базис бере участь і в читанні: член, чиї мітки
сходяться лише на цьому базисі, і сканується від нього, а кожен DVA на
ньому лягає на `база + 4 МіБ + зсув`, тож `list` і `dump` працюють на
розділі, створеному з іншим початком. F-62 зроблено наполовину: член,
у якого зникли власні мітки, можна прив'язати до листа, який називає
конфігурація сусідів, але не несе жоден просканований пристрій, —
через `--assume-member PATH[=GUID]`. Твердження дає лише слот: кожен
прочитаний через нього блок усе одно перевіряється контрольною сумою,
тож хибна прив'язка відхиляється, а не приймається. Без GUID прив'язка визначається
автоматично: пробується кожен вільний лист, сусіди цього top-level vdev
відкладаються настільки, наскільки дозволяє надлишковість, щоб обхід
мусив спиратися на кандидата, а пристрій із нулів у тому ж слоті
відділяє «слот має бути зайнятий» від «читається саме вміст цього
члена». Там, де доказ не обирає — листи одного дзеркала несуть однакові
байти, а достатньо широкий vdev реконструює навколо хибного слота, —
інструмент так і каже і просить GUID, а не вгадує. F-65, F-66 і F-67 теж уже в інструменті:
`--hints FILE` описує розкладку так, як це робив би шаблон `vdev_phys`, і
використовується точно як мітка; `--search-order` перебирає порядки
членів, які шаблон лишає відкритими, і лишає той, навколо якого не
доводиться нічого ремонтувати; `scan --emit-label` виписує цю розкладку
назад як передні 128 КіБ мітки, запечатані для своєї позиції і зупинені
перед кільцем уберблоків, — таку мітку можна покласти на копію диска й
читати чим завгодно. З голого випадку лишились F-63 (вивести базис
взагалі без уберблока) і F-64 (знайти MOS без уберблока) — територія
`zvolcarve`.

Звідси два режими:

* **Пошкодження в відомих межах** (затерто перші N MiB, переписано таблицю
  розділів, відрізано хвіст): не складний випадок. Усе поза межами
  читається штатно; L2/L3 чи їхні слоти знаходяться за магією і
  підтверджуються F-61; корінь береться з найновішого вцілілого uberblock-а.
  Покривають F-60–F-62.
* **Межі невідомі і всіх чотирьох міток нема**: базис береться з F-63, що
  вимагає повного проходу пристроєм — того самого, який усе одно потрібен
  carving-у, — а корінь із F-64.

`scan` повідомляє, звідки взято базис (мітка, таблиця розділів, сусід,
верифікатор uberblock-а, узгодженість вказівників, підказки користувача) і
скільки незалежних перевірок його підтвердили, тож журнал доказів фіксує
походження кожної адреси, яку використало витягання.

**Шлях практика: шаблон мітки, а не алгоритм.** Ті, хто робить це руками в
hex-редакторі, кажуть, що випадок голого диска на практиці рідко бував
складним: розкладка *відома* (кількість дисків, рівень RAIDZ, ashift,
приблизне місце розділу) з інших членів чи з матеріалів справи, шаблон
`vdev_phys` правиться під неї, і далі звичайний імпорт або професійні
комплекси відновлення ходять метаданими штатними засобами. Надійній
автоматизації опирається саме *здогадка* про топологію; все після неї
механічне. Тому інструмент лишає людину там, де людина сильніша, і
автоматизує те, що механічне й перевірюване:

| ID | Прі | Вимога |
|---|---|---|
| F-65 | S | **Підказки розкладки = віртуальна мітка.** Користувач може задати те, що ніс би шаблон `vdev_phys`: тип top-level vdev, список і порядок членів, `nparity`, `ashift`, кандидатів на базис, GUID пулу/vdev-а, якщо відомі, — і `scan`/`list`/`dump` використовують це так само, як справжню мітку. Шаблон живе лише в пам'яті і в журналі доказів; на пристрій нічого не пишеться (N-01). |
| F-66 | S | **Пошук у просторі підказок, підтвердження контрольною сумою.** Усе, що підказка лишає відкритим, перебирається і перевіряється, а не вгадується: порядок членів (6 членів RAIDZ2 = 720 перестановок, кожна вирішується контрольною сумою одного блока), `ashift` (кілька значень), базис (вікно вирівнювання), `nparity`. Кандидат приймається лише при збігу контрольних сум блоків (D-5); пошук зупиняється на першому повністю узгодженому шаблоні і звітує про всі альтернативи, що теж пройшли. |
| F-67 | S | **Експорт підтвердженої мітки.** `scan --emit-label FILE` записує відновлений nvlist `vdev_phys` (і геометрію як JSON) у файл, щоб покласти його на *копію* диска для `zpool import` чи завантажити в інший інструмент відновлення. Сам інструмент ніколи не кладе його на носій доказів. |

Порядок читання для голого випадку такий: підказки F-65 → пошук F-66 →
підтвердження F-61/F-62, де вцілів хоч якийсь матеріал міток → F-64 для
кореня → F-67, щоб передати результат далі. F-63 (зовсім без підказок)
лишається необов'язковим.

## 6. Нефункціональні вимоги

| ID | Вимога |
|---|---|
| N-01 | **Read-only за побудовою.** Evidence відкривається `O_RDONLY`; немає шляху коду, який відкриває вхід на запис. Вихідні шляхи відхиляються, якщо вони резолвляться на вхідний пристрій. |
| N-02 | **Без залежності від ядрового ZFS.** Працює на хості без завантаженого модуля ZFS і ніколи не викликає `zpool`/`zfs`. |
| N-03 | **Масштабується до пулів у багато TB.** Потокове витягання з обмеженою пам'яттю (ціль: ≤ 512 MiB RSS незалежно від розміру пулу, без опційних кешів). |
| N-04 | **Fail soft.** Пошкоджені метадані дають попередження і частковий результат, ніколи не crash; кожне переривання має чітку причину та код виходу. |
| N-05 | **Відтворюваність.** Однакові входи + однакові аргументи → побайтово однакові виходи та звіти (timestamp-и лише у визначених полях). |
| N-06 | **Портативність.** FreeBSD 13.x–15.x — першого класу; Linux (glibc/musl) збирається і проходить тести; macOS — best-effort. |
| N-07 | **Аудитованість.** Малий набір залежностей, без мережі, детерміновані збірки, підписані релізні архіви. |
| N-08 | **Продуктивність.** Послідовне витягання zvol ≥ 70 % від сирої швидкості читання пристрою на mirror; ≥ 40 % на RAIDZ2 (один потік), з опційним пулом воркерів для паралельних checksum/decompression. |
| N-09 | **Локалізація.** Рядки UI — англійською; документація ведеться англійською та українською. |

## 7. CLI (пропозиція)

Основний бінарник має рівно три команди. Деталі міток і uberblock-ів,
збирання пулу й топологія — це рівні verbosity команди `scan`, а не
окремі команди.

```
zvolrescue [глобальні опції] <команда> [опції] [аргументи]

Глобальні:
  -f, --format text|json      формат виводу (типово: text)
  -v, --verbose               повторюваний: -v додає кільця uberblock-ів, -vv — nvlist міток
  -q, --quiet
      --evidence-log FILE     дописувати JSON Lines лог evidence
      --no-color
      --debug                 трасувати кожне рішення читання у stderr (docs/DEBUGGING.uk.md)
      --debug-log FILE        та сама траса у FILE

Команди:
  scan  DEV...                          що на цих пристроях/образах: мітки, ім'я/GUID
                                        пулу, GUID vdev, вікно TXG, зібрана топологія,
                                        відсутні члени
  list  POOLSPEC [--txg N|--before TS] [--diff TXG2] [-r]
                                        dataset-и/zvol/знімки на TXG; для кожного
                                        знищеного — останній TXG, де він ще був
  dump  DATASET POOLSPEC -o OUT.img [--txg N] [--strict] [--key KEYSPEC] [--resume] [-r]
                                        витягти zvol (або дамп об'єктів ФС) у сирий
                                        sparse-образ із перевіркою кожного блоку;
                                        друкує SHA-256 виходу

POOLSPEC:  один або більше членів vdev, напр.
           /dev/ada0p3 /dev/ada1p3
           --image disk0.img --image disk1.img
           --pool-guid 0x1234…  (вибір серед кількох знайдених пулів)
KEYSPEC:   raw:FILE | hex:HEX | hex:@FILE | passphrase:FILE | prompt   (prompt читає stdin; echo не вимикається)
```

Коди виходу: `0` успіх, `1` помилка використання, `2` evidence нечитабельний,
`3` пул не відновлюваний на запитаному TXG, `4` витягання завершено з
помилками (лише `--strict`), `5` відмова (записало б в evidence).

Приклад (UC-1):

```sh
# 1. Що на цих дисках і які TXG ще доступні?
zvolrescue scan -v /dev/ada0p3 /dev/ada1p3

# 2. Коли зник pool/vm/disk0 і на якому TXG він ще був?
zvolrescue list /dev/ada0p3 /dev/ada1p3 -r | grep disk0

# 3. Витягти його з того TXG з перевіркою checksum.
zvolrescue dump pool/vm/disk0 /dev/ada0p3 /dev/ada1p3 --txg 4816230 \
    --strict -o /mnt/rescue/disk0.img --evidence-log case42.jsonl
```

### 7.1 Супутні інструменти

Усе, позначене ◇ у §5, виходить окремим бінарником, який лінкує ті самі
бібліотеки workspace. Назви попередні; кожен такий інструмент так само
атомарний, як основний:

| Інструмент | Робота | Вимоги |
|---|---|---|
| `zvoltimeline` | TXG ↔ час ↔ створення/знищення dataset-ів ↔ hostname/hostid; аналіз відкладених видалень | F-15, F-52 |
| `zvolcarve` | сканує сирий простір vdev на від'єднані zvol, оцінює кандидатів, передає їх у `dump` | F-41…F-43 |
| `zvolreport` | зведений forensic-звіт поверх логів evidence інших інструментів | F-51 |
| `zvolfiles` | дамп об'єктів і файлове відновлення ZPL з файлових dataset-ів | F-29, F-30 |

Основний бінарник ніколи не отримує їх як режими. Спільна поведінка
(лог evidence, JSON-вивід, коди виходу, read-only інваріанти) живе в
бібліотеці `zvol-common`, тож супутні інструменти успадковують її
задарма. Кожен інструмент описано в [COMPANIONS.uk.md](COMPANIONS.uk.md);
усі вони живуть у цьому репозиторії та workspace (рішення D-3, §13).

## 8. Архітектура

### 8.1 Мова та залежності

* **Rust** (stable, edition 2021; MSRV = stable-реліз, актуальний на старті етапу 0, підвищується свідомо). Обґрунтування: вхід за визначенням ворожий — пошкоджені метадані ніколи не повинні ронити інструмент чи читати за межами буфера (N-04), а slice-парсинг із перевіркою меж і `Result`-пропагація помилок дають це за замовчуванням. `cargo fuzz` закриває вимогу §9 щодо fuzzing одним target-ом на парсер. Один статичний бінарник (`-C target-feature=+crt-static` або musl-target на Linux) тривіально кладеться на rescue-носій. `rayon` дає паралельні checksum/decompression без data race (N-08).
* **Чистий Rust у стеку декодування**, тож для збірки не потрібні C-toolchain чи системні бібліотеки: `lz4_flex` (lz4), `ruzstd` (zstd, лише декодування), `flate2` з бекендом `miniz_oxide` (gzip); `lzjb` та `zle` реалізовані наново (тривіальні).
* Checksum-и: `fletcher2/4` наново; `sha2`, `blake3` із сімейства RustCrypto; `skein` (Skein-512-256 MAC з сіллю пулу як ключем) реалізовано наново в `zfs-ondisk::skein` (~200 рядків), бо crate RustCrypto не має режиму з ключем; для `edonr` реалізації на Rust нема — портовано з OpenZFS (`crates/edonr`, ~250 рядків, CDDL, окремий ізольований crate); перевірено на edonr-блоці справжнього `ztest`-пулу.
* Шифрування: `aes-gcm`, `ccm`, `pbkdf2` (RustCrypto); key-wrapping та розкладка IV/MAC з OpenZFS реалізовані наново.
* On-disk структури: `zerocopy`-представлення над `#[repr(C)]` визначеннями `blkptr_t`, `dnode_phys_t`, `uberblock_t` тощо — без копіювання і без `unsafe` у коді проєкту; парсер nvlist (XDR) написаний вручну.
* CLI: `clap` (derive); JSON: `serde` / `serde_json`; діагностика: `tracing`.
* Toolchain: `lang/rust` із ports на FreeBSD, `rustup` деінде. `#![forbid(unsafe_code)]` у кожному crate, крім `zvolrescue-io`, де кілька `libc`-викликів для доступу до пристроїв окремо рецензуються і коментуються.
* Перехресна перевірка з userland OpenZFS (`zdb`) робиться харнесом інтеграційних тестів: запуск бінарника `zdb` і diff виводу. FFI до `libzpool` нема.


Етап 0 створює `zvolrescue`, `zvolrescue-io`, `zfs-ondisk` і порожній
`zfs-read`; `zvol-common` виділяється з основного бінарника з появою
першого супутнього інструмента; модулі виносяться в окремі crate-и лише
коли цього вимагають час компіляції або розподіл відповідальності.

Кожен crate вище `zvolrescue-io` — чистий: приймає trait object
`BlockSource` і ніколи не торкається ОС, тому reader тривіально тестується
на in-memory fixture-ах і портативний.

### 8.3 Інваріанти безпеки

1. Трейт `BlockSource` має лише методи читання. Його єдина on-disk реалізація живе в `zvolrescue-io`, відкриває з `O_RDONLY` (плюс `O_EXCL` на платформах, які поважають його для блокових пристроїв) і є єдиним місцем, де вхідний шлях перетворюється на файловий дескриптор.
2. Вихідні шляхи канонізуються і порівнюються з `st_dev/st_ino` кожного входу; збіг → переривання з кодом 5.
3. Жодних `std::process::Command`, викликів shell, мережі: `cargo deny` забороняє мережеві crate-и, а тест перевіряє імпорти релізного бінарника на `socket`/`connect`/`execve`.
4. `#![forbid(unsafe_code)]` у кожному crate, крім `zvolrescue-io`; кожен `unsafe`-блок там має коментар `// SAFETY:` і покритий тестом.
5. Базис vdev (нульова точка) ніколи не береться на віру з таблиці розділів, мітки сусіда чи евристики: він використовується лише після того, як хоча б одна on-disk контрольна сума його підтвердила (§5.6), а `scan` називає підтверджувальний доказ.

## 9. Стратегія тестування

* **Unit-тести** для кожного парсера on-disk структур на «золотих» байтових масивах із реальних пулів.
* **Fixture-пули**, що генеруються в CI на FreeBSD-runner-і (GitHub Actions `vmactions/freebsd-vm` або власний хост FreeBSD) та на Linux з OpenZFS:
  * топології: single, mirror-2, raidz1-3, raidz2-4, raidz3-5, draid1;
  * dataset-и: zvol з відомим псевдовипадковим вмістом у кожній комбінації compression/checksum, sparse-zvol, шифровані zvol, дедупліковані zvol, знімки та клони;
  * сценарії: `zfs destroy` → відновлення на старішому TXG; `zpool destroy` → відновлення; один член відсутній; в одного члена занулені мітки; випадкове пошкодження 1 MiB у даних; випадкове пошкодження в метаданих.
  * перевірка: SHA-256 витягнутого образу дорівнює SHA-256, записаному до знищення.
* **Перехресна перевірка**: на хостах з userland OpenZFS порівнювати вивід `zvolrescue scan -v`/`list` із `zdb -l`/`zdb -u`/`zdb -d`.
* **Fuzzing**: `cargo fuzz` target-и для парсерів nvlist, blkptr, dnode і ZAP, запускаються обмежений час у CI на кожен push.
* **Статичний аналіз**: `cargo clippy -D warnings`, `cargo fmt --check`, `cargo deny` (ліцензії, advisories, заборонені crate-и); Miri на unit-тестах `zfs-ondisk`.

### 9.1 Золотий образ і матриця пошкоджень

Тести вище доводять, що читач розуміє on-disk формат. Вони не доводять, що
відновлення *правильне*, і нічого цього не доведе, доки правильна відповідь
не відома наперед. Тому справжній тест відновлення будується на одному
принципі: **спершу еталон, потім пошкодження, і результат інструмента
порівнюється з еталоном — ніколи з попереднім виводом самого інструмента.**
Це ж захищає від пастки реалізації, яку значною мірою пише ІІ: без
незалежного еталона алгоритм легко підігнати під один випадок і прийняти
за загальний.

**Якість, а не кількість.** Один золотий образ, а не багато. Варіюватись
мають *види пошкоджень та їхні комбінації*, а не дані: більше образів з
іншим вмістом додають час на збірку і жодного нового виду відмови. Один
образ робиться достатньо багатим, щоб кожному виду відмови було що
зачепити:

* **Один пул, кілька геометрій.** Один пул може мати top-level vdev-и
  різних типів (mirror, RAIDZ2, dRAID1 поруч, `zpool create -f`); ZFS
  розкладає кожен dataset по всіх, тож один образ проганяє всі шляхи
  реконструкції без трьох пулів.
* **Метадані, які варто ламати**: zvol-и з кількома `volblocksize`, розріджені
  й щільні, знімки, клони, перейменований том, знищений том і знищений
  знімок, шифрований dataset із raw-ключем і з passphrase, усі контрольні
  суми й стиснення, gang-блоки (низький поріг), великі dnode, відкладені
  видалення.
* **Багато версій**: сотні TXG із записами в томи між знімками, щоб кільця
  uberblock-ів були повні, старіші TXG вказували на вже змінені дані, а
  `--txg`, `--diff` і carving мали з чим працювати.
* **Оракул**, записаний поруч з образом при збірці: SHA-256 кожного тома на
  кожному знімку і на експорті, `zdb -d` кожного TXG, `zdb -l` кожного
  члена, `zpool status`, ключі. Це те «як має бути», з яким порівнюється
  кожен результат.

Образ збирається скриптом у справжньому ядерному середовищі (одна з
віртуалок у [REALWORLD-TESTS.uk.md](REALWORLD-TESTS.uk.md)) і далі
незмінний: це артефакт, ідентифікований своїм SHA-256, відтворюваний зі
скрипта і ніколи не правлений руками.

**Пошкодження прикладається, а не зберігається.** Кожен випадок — це
декларативний маніфест: член, діапазон байтів, шаблон (нулі, випадкові
байти, зсув на N секторів, старіша копія тієї ж структури поверх новішої,
поодинокі перевернуті біти), можливо кілька діапазонів на кількох членах —
і прикладається до тимчасової копії в момент тесту. Те, що практик робить
у hex-редакторі, записується один раз і відтворюється точно. Каталог
класів пошкоджень (мітки: одна, передня пара, задня пара, всі чотири, лише
`vdev_phys`, лише кільця, часткові кільця з підробленим txg; розділ:
переписана GPT, зсунутий початок, обрізаний хвіст, перестворений з іншим
розміром; метадані: MOS, dnode-блоки, непрямі блоки, ZAP властивостей,
крипто-об'єкт; дані: колонка RAIDZ, обидві половини дзеркала в різних
місцях, gang-заголовок, шифрований блок; цілий член відсутній; член,
замінений *старішою копією самого себе*) складається з семантики
надмірності ZFS, незалежно від поточного коду інструмента.

**Комбінаторика.** Класи ганяються поодинці, потім парами й трійками по
членах і геометріях; сотні прогонів по кілька секунд. Кожен прогін
потрапляє рівно в один із чотирьох результатів, а очікуваний результат
виводиться з надмірності, яку сама ZFS гарантує для цієї комбінації, а не
з того, що інструмент робить сьогодні:

1. відновлено біт-у-біт (хеш дорівнює оракулу);
2. відновлено через реконструкцію, і реконструкція видна в журналі доказів;
3. чиста відмова (код 3) без часткового виводу, поданого як добрий;
4. будь-що інше — дефект інструмента.

Інваріант «лише читання» перевіряється на кожному прогоні: хеші пошкоджених
копій входу після прогону не змінились. Частина комбінацій тримається поза
розробкою і ганяється лише перед релізом.

**Окремий репозиторій.** Образ, його оракул і маніфести пошкоджень живуть
у власному репозиторії (`zvolrescue-testdata`), щоб багатогігабайтні
артефакти не потрапляли в цей. Тут лишаються скрипт збірки, очікуваний
SHA-256 образу і CI-джоба, що завантажує образ і ганяє матрицю.

## 12. Відкриті питання

1. Чи етап 1 робити лише під FreeBSD, щоб рухатись швидше, а Linux CI додати на етапі 2? (Пропозиція: Linux CI з етапу 0 — генерація fixture там простіша, і код лишається портативним з першого дня.)
2. Розширення RAIDZ (`raidz_expansion`) — reflowed-розкладки: підтримати на етапі 2 чи відкласти?
3. `ruzstd` (чистий Rust, лише декодування) чи `zstd` (біндинги до libzstd): чистий Rust зберігає тривіальну статичну збірку, але повільніший. Заміряти на fixture-ах етапу 1; cargo feature може давати обидва.
4. Іменування та публікація crate-ів: тримати `zfs-ondisk` / `zfs-read` внутрішніми членами workspace чи опублікувати на crates.io як бібліотеки для повторного використання, коли API устаканиться?

Багатогігабайтним артефактам не місце в репозиторії з кодом. |
