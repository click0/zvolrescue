# Матриця тестів на реальних системах

**English version:** [REALWORLD-TESTS.md](REALWORLD-TESTS.md)

Що треба прогнати на справжніх системах, перш ніж довіряти `zvolrescue`
на дисках клієнта. CI покриває синтетичні fixture і userland-пули від
`ztest`; усе нижче потребує машини (або VM) зі справжнім ядровим ZFS,
справжніми блоковими пристроями і `zdb` цього дистрибутива.

Позначки: ☐ не запускалось · ◐ частково · ☑ пройшло · ✗ провал (посилання на issue).

## Середовища

| Середовище | Навіщо | Збірка ZFS | Примітки |
|---|---|---|---|
| **mfsBSD** (rescue-образ FreeBSD у RAM) | реалістичний rescue-носій: нема куди ставити, інструмент — статичний бінарник, скопійований мережею | базовий OpenZFS FreeBSD | статично злінкований `zvolrescue`; `mdconfig` для образів; `ztest` нема |
| **FreeBSD 14.x** | основна ціль (ТЗ N-06) | базовий OpenZFS 2.2 | `lang/rust` з ports/pkg; `zdb`, `ztest` у базі |
| **FreeBSD 15.x** | наступний реліз, новіші feature flags | базовий OpenZFS 2.3+ | очікувати `raidz_expansion`, `fast_dedup`, `longname` |
| **Debian stable** | найпоширеніший Linux-хост із `zfs-dkms` | zfs-dkms 2.2 (bookworm) | `apt install zfsutils-linux zfs-dkms`; loop-пристрої |
| **Ubuntu LTS** | ZFS у ядрі, поширено на хостах | zfs 2.2/2.3 | крос-перевірка CI вже тут (лише userland) |
| **CachyOS** (на базі Arch) | найсвіжіші ядро та OpenZFS git; першим ловить нові on-disk фічі | OpenZFS latest | `zfs-dkms` або `linux-cachyos-zfs`; типові `zstd`/`blake3` |

## Сценарії

Кожен сценарій — на кожному середовищі; фіксувати `zvolrescue --version`,
`zfs version`, ядро; для провалів додавати `--debug-log`.

### A. Гарантії read-only

| # | Сценарій | Критерій |
|---|---|---|
| A1 | `scan`/`list`/`dump` на сирому блоковому пристрої (`/dev/ada0p3`, `/dev/sdb2`) при **експортованому** пулі | пристрій незмінний (`sha256` перших і останніх 4 MiB до/після); `zpool import` працює |
| A2 | вихід на evidence-пристрої (`-o /dev/…` або файл на ФС, що живе на вході) | код 5, нічого не записано |
| A3 | запуск непривілейованим користувачем із правом читання пристрою | працює; привілеї не потрібні |

### B. Розкладки

| # | Пул | Критерій |
|---|---|---|
| B1 | один диск, ashift 9 і 12 | `list -r` == `zdb -d`; `dump` == `sha256` з `/dev/zvol/...` |
| B2 | mirror-2, один член відсутній | те саме з решти |
| B3 | raidz1 (3), raidz2 (4, 6), raidz3 (7) | те саме з `nparity` відсутніми членами |
| B4 | raidz з одним тихо зіпсованим членом (`dd` 1 MiB посередині) | `dump` лікує, у `--debug` видно відновлені блоки |
| B5 | пул із 2+ top-level vdev, mirror + raidz упереміш | те саме |
| B6 | пул з `log` і `cache` vdev | `scan` їх показує; `dump` не зачеплений |
| B7 | dRAID (`draid2:8d:1s`) | *очікувано не підтримується до F-25*; чиста відмова з кодом 3 |
| B8 | пул після `zpool attach`/`detach`/`replace` (застарілі мітки на старих дисках) | `scan` показує старого члена зі старішим txg і не змішує |
| B9 | vdev на цілому диску з GPT (Linux `-part1`, FreeBSD `p1`) | *потрібен F-06*: `scan` цілого диска знаходить ZFS-розділ |

### C. Властивості даних

| # | Властивість | Критерій |
|---|---|---|
| C1 | `compression=off,lz4,zstd,zstd-19,gzip-1,gzip-9,lzjb,zle` на томі | хеш `dump` збігається для кожного |
| C2 | `checksum=fletcher2,fletcher4,sha256,sha512,skein,edonr,blake3` | збігається; `skein`/`edonr` *чекають F-21* |
| C3 | `volblocksize=4K,8K,16K,64K,128K,1M` (потрібен `large_blocks`) | збігається |
| C4 | sparse-том із дірками, `zfs create -s -V 100G`, записано 1 GiB | образ sparse, `du` малий, хеш збігається |
| C5 | том із `dedup=on` і повторюваним вмістом | збігається |
| C6 | том зі знімками і клоном; `dump` для `vol@snap` і клону | кожен збігається зі своїм хешем |
| C7 | шифрований том (`encryption=aes-256-gcm`) з `--key raw:FILE` | *етап 3*; без ключа зараз код 64 |
| C8 | великі dnode (`dnodesize=auto`) на батьківській ФС | `list` не зачеплений |
| C9 | пул зі 100+ dataset-ами, глибока вкладеність, довгі імена (`longname` на FreeBSD 15) | `list -r` повний, збігається з `zdb -d` |

### D. Відновлення

| # | Сценарій | Критерій |
|---|---|---|
| D1 | `zfs destroy vol`, одразу експорт | `list --diff` показує знищеним; `dump` відновлює з попереднього txg, хеш збігається |
| D2 | `zfs destroy vol`, потім ще 500 MiB запису деінде, експорт | або відновлено зі старішого txg з кільця, або чисте «not found at any of N txgs» |
| D3 | `zpool destroy pool` | `scan` показує стан DESTROYED; `list`/`dump` працюють |
| D4 | пул, що не імпортується (`zpool import` → «I/O error») після занулення міток L0/L1 на одному члені | `scan` бере L2/L3; `dump` працює |
| D5 | пул із пошкодженим найновішим uberblock (занулити слот) | `list` бере попередній верифікований txg і каже про це |
| D6 | перервати `dump` SIGINT на ~50 %, потім `--resume` | фінальний хеш збігається, `resumed_from_block` > 0 |
| D7 | `dump -r pool/vm` з 5 томами | 5 образів + маніфест, хеші збігаються |

### E. Масштаб і пакування

| # | Сценарій | Критерій |
|---|---|---|
| E1 | том 2 TB на raidz2 із 4 HDD | швидкість ≥ 40 % сирого читання (ТЗ N-08); RSS ≤ 512 MiB |
| E2 | том 200 GB на NVMe-mirror | ≥ 70 % сирого читання |
| E3 | статична збірка FreeBSD запускається на mfsBSD 14 і 15 | `zvolrescue --version` і `scan` |
| E4 | `pkg`/ports на FreeBSD; `.deb` на Debian/Ubuntu; AUR на CachyOS | ставиться, є `man zvolrescue` (*пакування ще нема*) |

### F. Залізо

Різні контролери й накопичувачі змінюють, що означає «прочитати»;
інструмент ніколи не має покладатися на розмір сектора пристрою чи на
те, що він збігається з `ashift` пулу.

| # | Сценарій | Критерій |
|---|---|---|
| F1 | диски 512n, 512e (4 KiB фізичний / 512 логічний) і 4Kn, пули з `ashift=9` і `ashift=12` на кожному | `scan` показує `ashift` пулу, читання спираються лише на геометрію міток; хеші збігаються на всіх шести комбінаціях |
| F2 | ті самі образи через USB/UAS-міст, що транслює сектори (4K↔512), і напряму | однаковий вивід; якщо міст змінює видимий розмір пристрою, `scan` усе одно знаходить L2/L3 за розміром, який повідомляє ОС |
| F3 | HBA у режимі JBOD/IT (LSI/Broadcom, Adaptec) проти тих самих дисків на вбудованому AHCI | однаковий вивід |
| F4 | RAID-контролер із passthrough/«single-disk RAID0» і метаданими в кінці диска | `scan` знаходить чотири мітки за *повідомленим* розміром або попереджає, яких міток бракує |
| F5 | NVMe (кілька вендорів), SATA SSD, SAS | однаковий вивід; швидкість за E1/E2 |
| F6 | SMR (черепичний) HDD проти CMR | однаковий вивід; довгі послідовні читання не відвалюються за таймаутом; зафіксувати швидкість |
| F7 | диск із відомими bad-секторами (або `dm-flakey`/`dm-error` на Linux, `gnop -e 5 -r 10` на FreeBSD, що інжектять EIO) під дзеркалом | `dump` лікує з іншого члена; без надлишковості зануляються нечитабельні *сектори*, а не цілий блок (*читання по секторах при EIO — зробити*) |
| F8 | читання з диска з логічним сектором 4 KiB, коли пул `ashift=9` (створений на 512e, перенесений на 4Kn) | читання успішні (буферизований I/O); `--debug` показує обробку невирівняних зсувів |
| F9 | віртуальні диски: bhyve/QEMU virtio-blk з логічним 512 і 4096, VMware, Hyper-V; на `.img`/`.qcow2` (лише raw) | однаковий вивід |
| F10 | диск понад 2 TiB і 16 TiB (GPT, зсуви за межами 32/64-бітних лімітів секторів) | мітки знайдено за правильними кінцевими зсувами |
