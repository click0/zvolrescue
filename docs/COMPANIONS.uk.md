# Супутні інструменти — Технічне завдання

**Статус:** чернетка v0.1 · **Дата:** 2026-09-06 · **Батьківський документ:** [SPEC.uk.md](SPEC.uk.md) §3.0, §7.1
**English version:** [COMPANIONS.md](COMPANIONS.md)

Основний бінарник `zvolrescue` робить одну роботу (ТЗ §3.0). Усе, що
позначене ◇ у ТЗ §5, виконує один із чотирьох супутніх бінарників,
описаних тут. Усі вони живуть у цьому репозиторії та workspace (рішення
D-3 у ТЗ §13): один номер версії, один релізний архів, один CI, один
порт FreeBSD, що встановлює всі бінарники.

Кожен супутній інструмент так само атомарний, як основний: одна робота,
один статичний бінарник, без конфігурації, без демона, read-only щодо
evidence, чисті запуски. Вони ніколи не викликають один одного; дані
передаються лише через файли, які користувач називає в командному рядку.

---

## 1. Спільний контракт

Усе в цьому розділі реалізується один раз у бібліотечному crate
`zvol-common` і успадковується всіма п'ятьма бінарниками.

### 1.1 Аргументи

| Конвенція | Значення |
|---|---|
| `POOLSPEC` | як у ТЗ §7: пристрої, `--image FILE` (повторюваний), `--pool-guid GUID`. Обов'язковий `DATASET` завжди йде перед ним, бо перелік членів має змінну довжину. |
| `-f, --format text\|json` | текст для людей (типово), один JSON-документ на stdout для машин |
| `-v` / `-q` | більше / менше деталей, повторювані |
| `--evidence-log FILE` | дописати один JSON Lines запис на запуск (§1.3) |
| `--no-color` | без ANSI-кольорів; також автоматично, коли stdout — не термінал |
| `--txg N` / `--before TS` | вибір TXG, та сама семантика, що в `zvolrescue list` |
| `--key KEYSPEC` | ключ шифрування dataset-у, ті самі форми, що в `zvolrescue dump` |
| `-o PATH` | вихідний файл або каталог; відмова з кодом 5, якщо резолвиться на evidence |

### 1.2 Коди виходу

Ідентичні ТЗ §7: `0` ok, `1` використання, `2` evidence нечитабельний,
`3` пул не відновлюваний на TXG, `4` завершено з помилками, `5` відмова
(записало б в evidence). Інструменти з довгим скануванням додають `6` =
перервано, записано файл стану для продовження.

### 1.3 Запис логу evidence (версія формату 1)

Один JSON-об'єкт на рядок, лише дописування, ніколи не перезаписується:

```json
{"v":1,"ts":1757100010,"tool":"zvolcarve","version":"0.3.0","host":"rescue1",
 "argv":["zvolcarve","scan","--image","disk0.img","-o","/case42/carve"],
 "inputs":[{"path":"disk0.img","size":68719476736,"sha256":"…"}],
 "outputs":[{"path":"/case42/carve/cand-0007.img","size":10737418240,"sha256":"…"}],
 "result":{…специфічно для інструмента, ідентично документу -f json…},
 "status":0}
```

* `inputs[].sha256` є лише коли задано `--hash-inputs` (хешувати evidence
  на багато TB довго; вибір за користувачем).
* `outputs[].sha256` є завжди: кожен інструмент хешує те, що пише.
* Ці записи споживає `zvolreport`; більше їх ніхто не читає.

### 1.4 Read-only інваріанти

ТЗ §8.3 діє без змін: єдиний шлях від імені входу до файлового
дескриптора — `zvolrescue-io`, який відкриває `O_RDONLY`; без
`std::process::Command`, без мережі; `#![forbid(unsafe_code)]` поза
`zvolrescue-io`.

## 2. `zvoltimeline` — що сталося з пулом і коли

### 2.1 Робота

Перетворити TXG, які ще є на диску, на читабельну історію пулу: які
dataset-и, zvol і знімки існували на кожному TXG, коли вони з'явилися,
були перейменовані чи зникли, які хости імпортували пул, і — для всього
знищеного — останній TXG, де воно ще було, у вигляді готової команди
`zvolrescue dump`.

Відповідає на UC-3 і на перше питання UC-1 («коли він зник?»).

### 2.2 CLI

```
zvoltimeline POOLSPEC [--from TXG] [--to TXG] [--dataset NAME|GUID]
                      [--pending] [--hash-inputs] [-f text|json] [-o FILE]
```

Текстовий вивід — один рядок на подію, від найстарішої:

```
TXG       TIME                  EVENT      OBJECT                     DETAILS
4816201   2025-09-05T19:17:40Z  created    pool/vm/disk0              zvol 32G lz4 sha256
4816229   2025-09-05T19:20:05Z  snapshot   pool/vm/disk0@before-upgrade
4816230   2025-09-05T19:20:10Z  host       —                          hostid 0x1a2b3c4d "vmhost2"
4816231   2025-09-05T19:20:15Z  destroyed  pool/vm/disk0              last seen txg 4816230 → zvolrescue dump … --txg 4816230
4816232   —                     unreadable —                          MOS blocks overwritten
```

### 2.3 Вимоги

| ID | Прі | Вимога |
|---|---|---|
| T-01 | M | Перелічити кожен TXG, що має валідний uberblock у будь-якій мітці будь-якого члена (ТЗ F-04), плюс TXG checkpoint-у, якщо є. |
| T-02 | M | Для кожного TXG перелічити dataset-и з GUID, типом, іменем, TXG створення (повторно використовуючи dsl із `zfs-read`; ТЗ F-11/F-12). |
| T-03 | M | Diff сусідніх TXG у події: `created`, `destroyed`, `renamed` (той самий GUID, нове ім'я), `snapshot`, `snapshot-destroyed`, `clone`, `promoted`. |
| T-04 | M | TXG, чий MOS уже не читається (блоки перевикористано), звітується як `unreadable` з першим невдалим блоком і ніколи не перериває запуск. |
| T-05 | M | Для кожної події `destroyed` надрукувати останній TXG, що ще посилався на об'єкт, і точний командний рядок `zvolrescue dump`. |
| T-06 | S | Події `host` з nvlist міток: `hostid`, `hostname`, TXG мітки — виявляє імпорти на іншій машині. |
| T-07 | S | `--pending` (ТЗ F-15): по TXG — розмір free bpobj / deadlists, що ще тримають блоки знищених dataset-ів, щоб оцінити, чи дані фізично ще є. |
| T-08 | S | `--dataset` фільтрує події до одного об'єкта (за іменем на будь-якому TXG або за GUID). |
| T-09 | S | Зміни властивостей (`compression`, `volsize`, `encryption` …) як події `property` при `-v`. |
| T-10 | M | Детермінований порядок виводу: TXG, потім тип події, потім GUID об'єкта. |
| T-11 | S | Обмеження пам'яті: одночасно тримаються лише два знімки переліку dataset-ів. |

### 2.4 Приймання

Fixture-пул зі сценарною історією (create, snapshot, rename, destroy на
записаних TXG, імпорт на двох hostid): перелік подій дорівнює сценарію, а
надрукована команда `dump` для знищеного zvol відновлює його біт-у-біт.

## 3. `zvolcarve` — знайти zvol, на які вже не вказує жоден uberblock

### 3.1 Робота

Коли кільце uberblock-ів уже прокрутилося повз останній TXG, що посилався
на dataset, `zvolrescue list` його не бачить. `zvolcarve` сканує сирий
простір vdev на вцілілі метадані ZFS — dnode-и типу `DMU_OT_ZVOL` і дерева
indirect-блоків під ними, — відбудовує кандидатів zvol, оцінює їх і витягає
обрані користувачем із точно тією ж семантикою, що `zvolrescue dump` (той
самий бібліотечний код, той самий формат виходу, той самий запис
evidence).

### 3.2 CLI

```
zvolcarve scan    POOLSPEC -o DIR [--range VDEV:START-END] [--min-size BYTES]
                                  [--resume] [--hash-inputs] [-f text|json]
zvolcarve list    DIR                      показати кандидатів попереднього сканування
zvolcarve dump    DIR CANDIDATE -o OUT.img [--strict] [--key KEYSPEC] [--resume]
```

`DIR` — робочий каталог carving-у: індекс кандидатів (`candidates.json`),
сирий лог знахідок і стан сканування для продовження. Це єдине, що пише
`scan`.

### 3.3 Вимоги

| ID | Прі | Вимога |
|---|---|---|
| C-01 | M | Сканувати кожного члена (або `--range`) із гранулярністю `ashift`, потоково, з обмеженою пам'яттю; прогрес на stderr. |
| C-02 | M | Впізнавати dnode-блоки структурною валідацією: `dn_type` з відомого набору, `dn_indblkshift` 9–17, `dn_nlevels` 1–7, `dn_nblkptr` 1–3, відомі коди checksum/compression, DVA всередині vdev; діапазони кожного поля — з `dnode.h` OpenZFS. |
| C-03 | M | Впізнавати indirect-блоки: масиви block pointer-ів, чиї DVA лежать усередині членів vdev, а birth-TXG взаємно узгоджені. |
| C-04 | M | Від кожного dnode `DMU_OT_ZVOL` обійти його дерево, перевірити checksum-и і зібрати кандидата: оцінений `volsize`, діапазон birth-TXG, частка блоків, що пройшли перевірку, частка блоків, уже перезаписаних новішими даними. |
| C-05 | M | Оцінювати кандидатів (збіжність checksum, неперервність, узгодженість birth, частка перезаписаного) і сортувати за оцінкою; пояснювати оцінку при `-v`. |
| C-06 | S | Виявляти перезаписані блоки, звіряючи кожен DVA зі space map найновішого імпортованого TXG, коли він доступний. |
| C-07 | M | `dump` — побайтово той самий конвеєр, що `zvolrescue dump` (sparse-вихід, `--strict`, продовження, запис evidence); нечитабельні блоки стають нулями і логуються. |
| C-08 | M | `scan --resume` продовжує з файлу стану; переривання дає код 6. |
| C-09 | S | Члени mirror скануються один раз (ідентичні копії), члени RAIDZ/dRAID — з реконструкцією за парністю (етап 3+). |
| C-10 | S | Стиснуті метадані: пробувати lz4/zstd/gzip/lzjb на блоках-кандидатах, чия валідація в plaintext не вдалася. |
| C-11 | S | Також фіксувати знайдені dnode-и `DMU_OT_OBJSET`/dataset-ів, щоб кандидата можна було назвати, коли його DSL-метадані вціліли. |
| C-12 | C | Сигнатурний carving усередині даних кандидата (суперблоки UFS/ext4/NTFS, ТЗ F-43), щоб обмежити `volsize`, коли метадані втрачено. |

### 3.4 Приймання

Fixture: створити zvol із відомим вмістом, знищити, записати достатньо
сторонніх даних, щоб прокрутити всі 128 uberblock-ів повз нього, не
перевикористовуючи його блоки. `zvolrescue list` його вже не показує;
`zvolcarve scan` знаходить одного кандидата з оцінкою ≥ 0.95;
`zvolcarve dump` дає образ, чий SHA-256 дорівнює оригіналу.

## 4. `zvolreport` — один документ, який може перевірити третя сторона

### 4.1 Робота

Зібрати логи evidence, записані іншими інструментами, в один звіт із
перевірюваним ланцюжком хешів: який evidence досліджено, якими версіями
інструментів, якими командами, що витягнуто і чи кожен файл досі
збігається зі своїм записаним хешем.

### 4.2 CLI

```
zvolreport build   LOG... -o report.json [--md report.md] [--case ID] [--examiner NAME]
                          [--note TEXT]...
zvolreport verify  report.json [--evidence-root DIR] [--outputs-root DIR]
```

### 4.3 Вимоги

| ID | Прі | Вимога |
|---|---|---|
| R-01 | M | Розбирати записи evidence версії формату 1 (§1.3) з будь-якої кількості логів; невідомі версії відхиляти з чітким повідомленням. |
| R-02 | M | Розділи звіту: метадані справи; перелік evidence (шлях, розмір, хеш, якщо відомий); версії інструментів; кожна команда в хронологічному порядку зі статусом; зведення пулу та вікно TXG (із записів `scan`); витягання (dataset, TXG, вихід, розмір, хеш, кількість помилок); попередження. |
| R-03 | M | `build` — чистий: ті самі логи і прапорці дають той самий `report.json` побайтово (timestamp-и лише із записів). |
| R-04 | M | `verify` перераховує SHA-256 кожного переліченого виходу і кожного входу із записаним хешем; друкує таблицю PASS/FAIL по файлах; код 4 при будь-якому FAIL. |
| R-05 | S | Рендер у Markdown (`--md`), придатний для додавання до тікета чи forensic-справи. |
| R-06 | S | Виявляти прогалини: витягання з TXG поза записаним вікном, ніколи не хешовані виходи, записи від невідповідних версій інструментів. |
| R-07 | C | Підписувати `report.json` ключем ed25519 (`--sign KEYFILE`) і перевіряти підпис. |

### 4.4 Приймання

Прогнати UC-1 від початку до кінця з `--evidence-log`; `zvolreport build`
перелічує кожну команду і хеш; зміна одного байта витягнутого образу
змушує `zvolreport verify` впасти з кодом 4, назвавши цей файл.

## 5. `zvolfiles` — файли з файлових dataset-ів

### 5.1 Робота

Основний бінарник бачить файловий dataset щонайбільше як дамп об'єктів.
`zvolfiles` розуміє ZFS POSIX layer: каталоги, файли, симлінки, розширені
атрибути, власників і часові мітки — і витягає дерево каталогів або сирий
дамп об'єктів, коли метадані ZPL надто пошкоджені.

### 5.2 CLI

```
zvolfiles list     DATASET POOLSPEC [--txg N] [--key KEYSPEC] [PATH] [-R]
zvolfiles extract  DATASET POOLSPEC [--txg N] [--key KEYSPEC] [PATH...] -o DIR
                                    [--strict] [--preserve owner,times,xattr]
zvolfiles objects  DATASET POOLSPEC [--txg N] [--key KEYSPEC] -o DIR
```

### 5.3 Вимоги

| ID | Прі | Вимога |
|---|---|---|
| Z-01 | M | Читати master node ZPL, кореневий каталог і каталоги обох видів — micro-ZAP і fat-ZAP. |
| Z-02 | M | Декодувати system attributes (розкладка SA) для розміру, режиму, uid/gid, часів, кількості посилань; відкат на legacy-бонус `znode_phys`. |
| Z-03 | M | Звичайні файли, включно зі sparse-ділянками; симлінки (вбудовані в SA та об'єктні). |
| Z-04 | S | Розширені атрибути: на основі каталогів (`xattr=on`) і на основі SA (`xattr=sa`). |
| Z-05 | M | Маніфест `manifest.json` у вихідному каталозі: кожен витягнутий шлях із розміром, режимом, власником, часами, SHA-256 і кількістю помилок для цього файлу. |
| Z-06 | M | Нечитабельні блоки стають нулями з логуванням діапазону (ТЗ F-33); `--strict` натомість перериває. |
| Z-07 | S | Жорсткі посилання відновлюються як жорсткі посилання у вихідному каталозі, коли витягнуто обидва шляхи. |
| Z-08 | S | `objects` (ТЗ F-29): один файл на об'єкт плюс `objects.json` з метаданими dnode — запасний варіант, коли Z-01 не вдається. |
| Z-09 | S | Властивості dataset-у `casesensitivity`, `normalization` і `utf8only` враховуються при зіставленні `PATH`. |
| Z-10 | C | Великі dnode-и, project quotas та інші розширення розкладки SA через feature flags. |

### 5.4 Приймання

Fixture-файловий dataset із вкладеним деревом, sparse-файлами, симлінками,
xattr і жорсткими посиланнями, знищений після знімка його хешів:
`zvolfiles extract` на останньому доброму TXG відтворює дерево зі збіжними
хешами та метаданими; `objects` дає той самий вміст файлів, коли ZAP
кореневого каталогу навмисно занулено.

## 6. Поставка

Супутні інструменти йдуть за етапами ТЗ §10; жоден не виходить до
приймання етапу 1 основного бінарника, бо всі залежать від шарів dsl/zvol
у `zfs-read`.

| Етап | Інструмент | Обсяг |
|---|---|---|
| 3 | `zvoltimeline` | T-01…T-05, T-10 |
| 3 | `zvolcarve` | сканування single/mirror, C-01…C-05, C-07, C-08 |
| 3 | `zvolreport` | R-01…R-04 |
| 4 | `zvolfiles` | Z-01…Z-03, Z-05, Z-06 |
| пізніше | усі | решта рядків S/C; `zvolcarve` на RAIDZ/dRAID |

Кожен інструмент — член workspace `crates/<tool>/` із власними
`README.md`, man-сторінкою (`<tool>.1`) та інтеграційними тестами в
`tests/<tool>/`. Релізний архів і порт FreeBSD встановлюють усі бінарники
та man-сторінки разом.
