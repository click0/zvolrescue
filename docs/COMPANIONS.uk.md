# Супутні інструменти — Технічне завдання

**Статус:** чернетка v0.1 · **Дата:** 2026-09-06 · **Батьківський документ:** [SPEC.uk.md](SPEC.uk.md) §3.0, §7.1

**English version:** [COMPANIONS.md](COMPANIONS.md)

Основний бінарник `zvolrescue` робить одну роботу (ТЗ §3.0). Усе, що
позначене ◇ у ТЗ §5, виконує один із чотирьох супутніх бінарників,
описаних тут. Усі вони живуть у цьому репозиторії та workspace (рішення
D-3 у ТЗ §13): один номер версії, один релізний архів, один CI, один
порт FreeBSD, що встановлює всі бінарники.

Кожен супутній інструмент так само атомарний, як основний: одна робота,
один статичний бінарник, без конфігурації, без демона, read-only щодо
evidence, чисті запуски. Вони ніколи не викликають один одного; дані
передаються лише через файли, які користувач називає в командному рядку.

---

## 1. Спільний контракт

Усе в цьому розділі реалізується один раз у бібліотечному crate
`zvol-common` і успадковується всіма п'ятьма бінарниками.

### 1.1 Аргументи

| Конвенція | Значення |
|---|---|
| `POOLSPEC` | як у ТЗ §7: пристрої, `--image FILE` (повторюваний), `--pool-guid GUID`. Обов'язковий `DATASET` завжди йде перед ним, бо перелік членів має змінну довжину. |
| `-f, --format text\|json` | текст для людей (типово), один JSON-документ на stdout для машин |
| `-v` / `-q` | більше / менше деталей, повторювані |
| `--evidence-log FILE` | дописати один JSON Lines запис на запуск (§1.3) |
| `--no-color` | без ANSI-кольорів; також автоматично, коли stdout — не термінал |
| `--txg N` / `--before TS` | вибір TXG, та сама семантика, що в `zvolrescue list` |
| `--key KEYSPEC` | ключ шифрування dataset-у, ті самі форми, що в `zvolrescue dump` |
| `-o PATH` | вихідний файл або каталог; відмова з кодом 5, якщо резолвиться на evidence |

### 1.2 Коди виходу

Ідентичні ТЗ §7: `0` ok, `1` використання, `2` evidence нечитабельний,
`3` пул не відновлюваний на TXG, `4` завершено з помилками, `5` відмова
(записало б в evidence). Інструменти з довгим скануванням додають `6` =
перервано, записано файл стану для продовження.

### 1.3 Запис логу evidence (версія формату 1)

Один JSON-об'єкт на рядок, лише дописування, ніколи не перезаписується:

```json
{"v":1,"ts":1757100010,"tool":"zvolcarve","version":"0.3.0","host":"rescue1",
 "argv":["zvolcarve","scan","--image","disk0.img","-o","/case42/carve"],
 "inputs":[{"path":"disk0.img","size":68719476736,"sha256":"…"}],
 "outputs":[{"path":"/case42/carve/cand-0007.img","size":10737418240,"sha256":"…"}],
 "result":{…специфічно для інструмента, ідентично документу -f json…},
 "status":0}
```

* `inputs[].sha256` є лише коли задано `--hash-inputs` (хешувати evidence
  на багато TB довго; вибір за користувачем).
* `outputs[].sha256` є завжди: кожен інструмент хешує те, що пише.
* Ці записи споживає `zvolreport`; більше їх ніхто не читає.

### 1.4 Read-only інваріанти

ТЗ §8.3 діє без змін: єдиний шлях від імені входу до файлового
дескриптора — `zvolrescue-io`, який відкриває `O_RDONLY`; без
`std::process::Command`, без мережі; `#![forbid(unsafe_code)]` поза
`zvolrescue-io`.

## 2. `zvoltimeline` — що сталося з пулом і коли

### 2.1 Робота

Перетворити TXG, які ще є на диску, на читабельну історію пулу: які
dataset-и, zvol і знімки існували на кожному TXG, коли вони з'явилися,
були перейменовані чи зникли, які хости імпортували пул, і — для всього
знищеного — останній TXG, де воно ще було, у вигляді готової команди
`zvolrescue dump`.

Відповідає на UC-3 і на перше питання UC-1 («коли він зник?»).

### 2.2 CLI

```
zvoltimeline POOLSPEC [--from TXG] [--to TXG] [--dataset NAME|GUID]
                      [--pending] [--hash-inputs] [-f text|json] [-o FILE]
```

Текстовий вивід — один рядок на подію, від найстарішої:

```
TXG       TIME                  EVENT      OBJECT                     DETAILS
4816201   2025-09-05T19:17:40Z  created    pool/vm/disk0              zvol 32G lz4 sha256
4816229   2025-09-05T19:20:05Z  snapshot   pool/vm/disk0@before-upgrade
4816230   2025-09-05T19:20:10Z  host       —                          hostid 0x1a2b3c4d "vmhost2"
4816231   2025-09-05T19:20:15Z  destroyed  pool/vm/disk0              last seen txg 4816230 → zvolrescue dump … --txg 4816230
4816232   —                     unreadable —                          MOS blocks overwritten
```

### 2.3 Вимоги

| ID | Прі | Вимога |
|---|---|---|
| T-01 | M | Перелічити кожен TXG, що має валідний uberblock у будь-якій мітці будь-якого члена (ТЗ F-04), плюс TXG checkpoint-у, якщо є. |
| T-02 | M | Для кожного TXG перелічити dataset-и з GUID, типом, іменем, TXG створення (повторно використовуючи dsl із `zfs-read`; ТЗ F-11/F-12). |
| T-03 | M | Diff сусідніх TXG у події: `created`, `destroyed`, `renamed` (той самий GUID, нове ім'я), `snapshot`, `snapshot-destroyed`, `clone`, `promoted`. |
| T-04 | M | TXG, чий MOS уже не читається (блоки перевикористано), звітується як `unreadable` з першим невдалим блоком і ніколи не перериває запуск. |
| T-05 | M | Для кожної події `destroyed` надрукувати останній TXG, що ще посилався на об'єкт, і точний командний рядок `zvolrescue dump`. |
| T-06 | S | Події `host` з nvlist міток: `hostid`, `hostname`, TXG мітки — виявляє імпорти на іншій машині. |
| T-07 | S | `--pending` (ТЗ F-15): по TXG — розмір free bpobj / deadlists, що ще тримають блоки знищених dataset-ів, щоб оцінити, чи дані фізично ще є. |
| T-08 | S | `--dataset` фільтрує події до одного об'єкта (за іменем на будь-якому TXG або за GUID). |
| T-09 | S | Зміни властивостей (`compression`, `volsize`, `encryption` …) як події `property` при `-v`. |
| T-10 | M | Детермінований порядок виводу: TXG, потім тип події, потім GUID об'єкта. |
| T-11 | S | Обмеження пам'яті: одночасно тримаються лише два знімки переліку dataset-ів. |

### 2.4 Приймання

Fixture-пул зі сценарною історією (create, snapshot, rename, destroy на
записаних TXG, імпорт на двох hostid): перелік подій дорівнює сценарію, а
надрукована команда `dump` для знищеного zvol відновлює його біт-у-біт.

*Стан: T-01…T-06, T-08, T-10 і T-11 реалізовані й перевіряються в CI на
mirror-фікстурі (три транзакційні групи, том знищено на найновішій):
перелік подій — той самий, що в сценарії, а надрукована командою `dump`
відновлює том із тим самим SHA-256, який уже закріплено e2e-кроком.
`--pending` (T-07) повідомляє, скільки простору ZFS уже відпустив, але
ще не звільнив: `free_bpobj` пулу і deadlist кожного dataset-а,
прочитані з їхніх bonus-буферів, тож відповідь не коштує жодного обходу.
Поки блок там ще враховується, він не перерозподілений — а це і є
різниця між знищеним dataset-ом, який ще можна відновити, і тим, який
уже ні. Це число звіряється з власним обліком bpobj у `zdb` на кожному
пулі `ztest` у CI. Події властивостей (T-09) повідомляються для тих
властивостей, які цей читач знає, — `volsize`, `volblocksize` і набір
шифрування, — а не для кожної властивості dataset-а. Пул `ztest` ганяє той самий код на справжніх on-disk байтах,
разом із транзакційними групами, чий MOS уже не обходиться, але власної
сценарної історії не має.*

## 3. `zvolcarve` — знайти zvol, на які вже не вказує жоден uberblock

### 3.1 Робота

Коли кільце uberblock-ів уже прокрутилося повз останній TXG, що посилався
на dataset, `zvolrescue list` його не бачить. `zvolcarve` сканує сирий
простір vdev на вцілілі метадані ZFS — dnode-и типу `DMU_OT_ZVOL` і дерева
indirect-блоків під ними, — відбудовує кандидатів zvol, оцінює їх і витягає
обрані користувачем із точно тією ж семантикою, що `zvolrescue dump` (той
самий бібліотечний код, той самий формат виходу, той самий запис
evidence).

### 3.2 CLI

```
zvolcarve scan    POOLSPEC -o DIR [--range VDEV:START-END]
                                  [--volblocksize BYTES] [--levels N]
                                  [--txg FROM..TO] [--size MIN..MAX]
                                  [--dnode-type TYPE...] [--profile FILE]
                                  [--like DATASET] [--strict-profile]
                                  [--resume] [--hash-inputs] [-f text|json]
zvolcarve list    DIR                      показати кандидатів попереднього сканування
zvolcarve dump    DIR CANDIDATE -o OUT.img [--strict] [--key KEYSPEC] [--resume]
```

`DIR` — робочий каталог carving-у: індекс кандидатів (`candidates.json`),
сирий лог знахідок і стан сканування для продовження. Це єдине, що пише
`scan`.

### 3.3 Вимоги

| ID | Прі | Вимога |
|---|---|---|
| C-01 | M | Сканувати кожного члена (або `--range`) із гранулярністю `ashift`, потоково, з обмеженою пам'яттю; прогрес на stderr. |
| C-02 | M | Впізнавати dnode-блоки структурною валідацією: `dn_type` з відомого набору, `dn_indblkshift` 9–17, `dn_nlevels` 1–7, `dn_nblkptr` 1–3, відомі коди checksum/compression, DVA всередині vdev; діапазони кожного поля — з `dnode.h` OpenZFS. |
| C-03 | M | Впізнавати indirect-блоки: масиви block pointer-ів, чиї DVA лежать усередині членів vdev, а birth-TXG взаємно узгоджені. |
| C-04 | M | Від кожного dnode `DMU_OT_ZVOL` обійти його дерево, перевірити checksum-и і зібрати кандидата: оцінений `volsize`, діапазон birth-TXG, частка блоків, що пройшли перевірку, частка блоків, уже перезаписаних новішими даними. |
| C-05 | M | Оцінювати кандидатів (збіжність checksum, неперервність, узгодженість birth, частка перезаписаного) і сортувати за оцінкою; пояснювати оцінку при `-v`. |
| C-06 | S | Виявляти перезаписані блоки, звіряючи кожен DVA зі space map найновішого імпортованого TXG, коли він доступний. |
| C-07 | M | `dump` — побайтово той самий конвеєр, що `zvolrescue dump` (sparse-вихід, `--strict`, продовження, запис evidence); нечитабельні блоки стають нулями і логуються. |
| C-08 | M | `scan --resume` продовжує з файлу стану; переривання дає код 6. |
| C-09 | S | Члени mirror скануються один раз (ідентичні копії), члени RAIDZ/dRAID — з реконструкцією за парністю (етап 3+). |
| C-10 | S | Стиснуті метадані: пробувати lz4/zstd/gzip/lzjb на блоках-кандидатах, чия валідація в plaintext не вдалася. |
| C-11 | S | Також фіксувати знайдені dnode-и `DMU_OT_OBJSET`/dataset-ів, щоб кандидата можна було назвати, коли його DSL-метадані вціліли. |
| C-12 | C | Сигнатурний carving усередині даних кандидата (суперблоки UFS/ext4/NTFS, ТЗ F-43), щоб обмежити `volsize`, коли метадані втрачено. |

#### Профіль пошуку

Пул, що пережив сто тисяч транзакційних груп, тримає куди більше
впізнаваних метаданих, ніж належить шуканому об'єктові: dnode-и кожного
dataset-а, який колись існував, і indirect-блоки кожного покоління
кожного дерева. Структурна валідація (C-02) каже лише «це dnode»; вона не
каже «це може бути той загублений том на 300 ГБ». Друге зазвичай знає
оператор — розмір блока тому, якої глибини мусило бути його дерево,
приблизно коли його писали, приблизно якого він був розміру, — і саме це
знання перетворює скан із мільйонів влучань на кілька кандидатів.

Профіль — це **фільтр, а не припущення**: він вирішує, за чим варто йти, і
ніщо з видобутого не стає довіреним лише тому, що збіглося з профілем.
Кожен блок, який отримує `dump`, так само перевіряється власною
контрольною сумою — точно як у головному бінарнику.

| ID | Прі | Вимога |
|---|---|---|
| C-13 | M | **Профіль пошуку** звужує те, що вважається кандидатом, *на етапі впізнавання* — до того, як обійдено чи оцінено бодай одне дерево: `--volblocksize` (розмір блока даних), `--levels` (`dn_nlevels`, тобто глибина дерева L0…Ln), `--txg FROM..TO` (вікно birth-TXG), `--size MIN..MAX` (оцінений `volsize`), `--dnode-type` (типово `zvol`). Застосовувати його під час впізнавання, а не після — у цьому й суть: пошук одного тому на 300 ГБ не має оплачувати обхід дерев усього іншого в пулі. |
| C-14 | M | Кожне поле профілю необов'язкове й незалежне; відсутнє поле не фільтрує нічого. Профіль, який нічого не знайшов, мусить бути видимою *відмовою*, а не порожнечею: прогін повідомляє, скільки влучань відкинуло кожне поле, щоб «0 кандидатів, 4,2 млн dnode відкинуто за volblocksize» відрізнялося від «на цьому диску нема нічого». |
| C-15 | M | Лічильники відмов за причинами — тип dnode, `indblkshift`, `nlevels`, `nblkptr`, DVA поза межами будь-якого члена, birth-TXG поза вікном, розмір поза діапазоном, невідомий код checksum/compression — на stderr як прогрес і в JSON-результаті, щоб оператор бачив, яке саме одне поле затісне, і послабив саме його. |
| C-16 | S | `--profile FILE`: ті самі поля як JSON-документ, щоб кейс можна було перезапустити, переглянути й передати; застосований профіль дослівно копіюється в запис evidence (§1.3), бо список кандидатів нічого не вартий без фільтра, який його породив. |
| C-17 | S | `--like DATASET`: узяти `volblocksize`, `nlevels` і `volsize` з dataset-а, який *ще* існує в пулі, і використати як профіль. У більшості інцидентів утрачений том створювали так само, як сусідів, і вцілілий сусід — краще джерело цих чисел, ніж пам'ять оператора. |
| C-18 | S | Поля профілю типово є *підказками*: влучання, яке не пройшло м'яке поле, все одно записується — із назвою поля, що не зійшлося, — і ранжується нижче за ті, що зійшлися, тож хибна здогадка коштує місця в списку, а не всього відновлення. `--strict-profile` перетворює їх на жорсткі фільтри для випадків, коли оператор упевнений, а скан інакше був би надто повільним. |
| C-19 | C | Автопрофіль: без заданого профілю `scan --sample N` читає перші N влучань і показує гістограми `volblocksize`, `nlevels` і birth-TXG, які трапились, щоб оператор обрав профіль із того, що справді є на диску, а не вгадував. |

### 3.4 Приймання

Fixture: створити zvol із відомим вмістом, знищити, записати достатньо
сторонніх даних, щоб прокрутити всі 128 uberblock-ів повз нього, не
перевикористовуючи його блоки. `zvolrescue list` його вже не показує;
`zvolcarve scan` знаходить одного кандидата з оцінкою ≥ 0.95;
`zvolcarve dump` дає образ, чий SHA-256 дорівнює оригіналу.

Для профілю: та сама fixture, але в пулі присутні ще три zvol-и інших
розмірів блока і розмірів. Скан без профілю знаходить усіх чотирьох
кандидатів; скан із `--volblocksize` і `--size` знищеного тому знаходить
саме його, а решту трьох показує як відкинутих, називаючи поле, що
відкинуло кожного; профіль, який не підходить жодному, дає нуль
кандидатів *і* ненульовий лічильник відмов для винного поля. Видобутий
образ у кожному випадку побайтово однаковий, бо профіль не торкається
того, що перевіряє `dump`.

*Стан: C-01…C-05, C-07, C-08, C-10 і C-13…C-18 реалізовані, а
приймальний прогін — крок у CI на фікстурі, де том лежить на членах, а
жоден уберблок про нього не згадує на жодній транзакційній групі:
`zvolrescue list` показує лише `tank` і `tank/vm`, `zvolcarve scan`
ставить dnode тому першим, а `zvolcarve dump` дає той самий SHA-256, що
вже закріплений витяганням через обхід. Там же перевіряється: кожен
кандидат, що не пройшов профіль, стоїть нижче за будь-якого, що пройшов;
порожній результат називає поле, яке його спорожнило; профіль, знятий із
вцілілого сусіда, несе його числа; а перерваний і продовжений скан
дорівнює одному проходу.

Дві деталі — фікстури, а не інструмента: у її тому dnode має один рівень
і більше блоків, ніж покривають його вказівники, а такої форми OpenZFS
не пише, тож він втрачає частину структурної оцінки і має 0.94 замість
≥ 0.95, яких вимагає цей розділ; сама ж перевірка форми правильна, і том
однаково стоїть першим із великим відривом. І розмір, на який
видобувається викарбуваний том, — той, що випливає з його dnode, бо ZAP
`zvol_prop`, який знав `volsize`, з викарбуваного dnode недосяжний;
`--size` дає справжній, коли він відомий.

C-09 виконується для RAIDZ і dRAID з одним винятком, і CI покриває це на
raidz2-фікстурі: dnode має 512 байт і лежить цілком усередині одного
сектора розподілу на одній колонці, тож упізнавання на члені працює там
так само, як на дзеркалі, а видобування йде через пул, тобто
відновлюється з парності при відсутніх членах — той самий образ вийшов
із raidz2-карвінгу, де двох членів із чотирьох не було. Виняток —
стиснений прохід: стиснений блок розрізаний по колонках, тож жоден член
не тримає його суцільно, і стиснені метадані скануванням сирих байтів
знаходять лише дзеркала й одиночні диски. Це виправило б читання
логічного простору замість фізичного, але воно потребує відображення на
кожен розмір блока окремо, щоб окупитися.

C-11 і C-19 реалізовані й покриті в CI. Викарбуваний dnode не несе
імені — імена живуть у ланцюжку каталогів DSL у MOS, до якого карвінг
саме й не дістає, — тож скан лишає кожен dnode dataset-а, який зустрів,
хоч би що просив профіль, і кандидат називається GUID-ом та
транзакційною групою створення того dataset-а, чий objset досі вказує на
нього. Цього досить, щоб зіставити з рядком `zvoltimeline`. `--sample N`
показує, який вигляд насправді мають перші N влучань — типи об'єктів,
розміри блоків, глибини дерев і транзакційні групи народження, — щоб
профіль можна було взяти з диска, а не з пам'яті.

C-06 реалізовано. Space map кожного метаслаба відтворюється в множину
діапазонів, і про кожен блок, який заявляє кандидат, питають: місце або
досі видане, або звільнене. Ні те, ні те не є вироком про дані — вирок
виносить контрольна сума, і ранжування вже читає кожен блок, — тож на
оцінку кандидата це не впливає. Додає воно різницю між *перезаписано* і
*звільнено, але ще не перезаписано*: даними, які сходяться сьогодні й
можуть не зійтися завтра, а це і є різниця між відновленням, яке варто
починати зараз, і тим, яке вже спізнилось.

Дві речі, які варто знати про цю відповідь. Вона відстає: пул тримає
свіжі видачі в лог-мапах, ще не злитих у метаслаби, тож місце, видане в
останні кілька транзакційних груп, може читатись як вільне — помилка
спрямована в один бік, і звіт про це каже (`may_lag`). І vdev, чия
конфігурація не каже, де його метаслаби (розкладка, задана руками),
пропускається поіменно, а його блоки повідомляються як необліковані, а
не як вільні.

Декодер перевіряється в CI тим єдиним числом, яке ZFS веде незалежно від
журналу, що ми відтворюємо, — `smp_alloc` у заголовку кожної мапи.
Відтворення всіх метаслабів кожного пулу `ztest` дає байт у байт те, що
zdb читає з тих заголовків.

C-12 реалізовано, і він відповідає на те питання, на яке карвінг інакше
відповісти не може. Dnode каже, скільки блоків має об'єкт, а це не те,
на який розмір зроблено том: у тому, чий хвіст ніколи не писався, блоків
менше. А от те, що *всередині*, зазвичай каже — майже кожна файлова
система пише суперблок на фіксованому зсуві біля початку, і в ньому
розмір, на який її зробили. ext2/3/4, swap, XFS, btrfs, NTFS, FAT32
дають розмір; UFS2, LUKS, GPT і вкладена мітка ZFS упізнаються без
нього, бо здогад без числа — чесний, а вигадане число — ні.

`dump` бере розмір спершу з `--size`, потім із того, що том містить, і
лише потім із того, що випливає з dnode, — і каже, звідки. На фікстурі,
чий том несе суперблок ext4, зроблений на 32 МіБ, тоді як його dnode має
чотири блоки по 8 КіБ, карвінг без заданого розміру дає той самий образ,
що й видобування через обхід, байт у байт.

Сигнатури перевіряються в CI на файлових системах, які раннер справді
створює через `mkfs.ext4` і `mkswap`, — це те єдине місце, де це можна
звірити з чимось, окрім власної думки.

C-10 реалізовано для всіх чотирьох кодеків, і причина, чому не лише
lz4, — у тому, що провал сканування тільки з lz4 мовчазний. Пул,
створений до фічі `lz4_compress`, тримає метадані в lzjb; сканування,
яке пробує самий лише lz4, не знайде на ньому жодного dnode — і це
виглядає точнісінько як член, на якому метаданих ніколи й не було. Тому
`scan` типово пробує lz4, lzjb, gzip і zstd, а `--compressed` називає,
які саме пробувати: підмножину, коли історія пулу відома, чи `none` —
самий лише plaintext-прохід. Нерозпізнану назву відхилено з кодом
виходу 1, а не тихо пропущено, бо друкарська помилка, що мовчки вимикає
кодек, — це той самий мовчазний провал.

У кожного кодека спершу питають, чи можуть ці байти бути його власними:
чотирибайтова довжина lz4 у big-endian, пара «метод і контрольне число»
gzip, магія zstd, — тож повну спробу розпакування на кожному слоті
платить лише lzjb, який не має заголовка взагалі. На 100 МБ члена
`ztest`-пулу сам plaintext-прохід займає 0,02 с, lz4 додає 0,9 с,
lzjb — 0,2 с, gzip — 0,03 с, zstd — 0,15 с; усі чотири разом — 1,15 с.
Це й є ціна того, щоб не мусити заздалегідь знати, хто писав пул.*

## 4. `zvolreport` — один документ, який може перевірити третя сторона

### 4.1 Робота

Зібрати логи evidence, записані іншими інструментами, в один звіт із
перевірюваним ланцюжком хешів: який evidence досліджено, якими версіями
інструментів, якими командами, що витягнуто і чи кожен файл досі
збігається зі своїм записаним хешем.

### 4.2 CLI

```
zvolreport build   LOG... -o report.json [--md report.md] [--case ID] [--examiner NAME]
                          [--note TEXT]... [--sign KEYFILE] [--signature report.json.sig]
zvolreport verify  report.json [--evidence-root DIR] [--outputs-root DIR]
                          [--key KEYFILE] [--signature report.json.sig]
zvolreport keygen  -o KEY [--public KEY.pub]
```

### 4.3 Вимоги

| ID | Прі | Вимога |
|---|---|---|
| R-01 | M | Розбирати записи evidence версії формату 1 (§1.3) з будь-якої кількості логів; невідомі версії відхиляти з чітким повідомленням. |
| R-02 | M | Розділи звіту: метадані справи; перелік evidence (шлях, розмір, хеш, якщо відомий); версії інструментів; кожна команда в хронологічному порядку зі статусом; зведення пулу та вікно TXG (із записів `scan`); витягання (dataset, TXG, вихід, розмір, хеш, кількість помилок); попередження. |
| R-03 | M | `build` — чистий: ті самі логи і прапорці дають той самий `report.json` побайтово (timestamp-и лише із записів). |
| R-04 | M | `verify` перераховує SHA-256 кожного переліченого виходу і кожного входу із записаним хешем; друкує таблицю PASS/FAIL по файлах; код 4 при будь-якому FAIL. |
| R-05 | S | Рендер у Markdown (`--md`), придатний для додавання до тікета чи forensic-справи. |
| R-06 | S | Виявляти прогалини: витягання з TXG поза записаним вікном, ніколи не хешовані виходи, записи від невідповідних версій інструментів. |
| R-07 | C | Підписувати `report.json` ключем ed25519 (`--sign KEYFILE`) і перевіряти підпис. |

### 4.4 Приймання

Прогнати UC-1 від початку до кінця з `--evidence-log`; `zvolreport build`
перелічує кожну команду і хеш; зміна одного байта витягнутого образу
змушує `zvolreport verify` впасти з кодом 4, назвавши цей файл.

*Стан: R-01…R-07 реалізовані, і саме цей приймальний прогін — крок у CI
на mirror-фікстурі: `scan`, `zvoltimeline` і `dump` в один лог, далі
`build`, далі `verify` до і після зміни байта, і ще раз — коли образ
прибрано. `build` перевіряється на побайтову однаковість другого прогону
(R-03); запис із форматом, відмінним від 1, валить `build`, а не
пропускається (R-01).

R-07 реалізовано, і суть його в тому, що підпис переживає цей
інструмент. `build --sign KEY` підписує точні байти `report.json`
алгоритмом Ed25519 і кладе поруч сирі 64 байти; `verify --key KEY.pub`
їх перевіряє. Ключі — у тому вигляді, який пише й читає OpenSSL:
незашифрований PKCS#8 для приватної половини, SubjectPublicKeyInfo для
відкритої, обидва в PEM або в голому DER, — тож третя сторона, яка не
має жодної копії `zvolrescue`, перевірить звіт через

```
openssl pkeyutl -verify -pubin -inkey key.pub -rawin \
    -in report.json -sigfile report.json.sig
```

а `keygen` пише пару, яку OpenSSL читає як свою власну. Саме це й
перевіряє CI, в обидва боки: OpenSSL перевіряє підпис, який зробив цей
інструмент, цей інструмент перевіряє підпис, який зробив OpenSSL, і
відкритий ключ, який кожен виводить із приватного ключа іншого,
побайтово однаковий. Підпис, який може перевірити лише інструмент його
автора, — це не ланцюг зберігання доказів, це звичка.

Підпис перевіряється до того, як документ розбирають, бо він — над
байтами й розбору не потребує, і бо відредагований звіт часто взагалі
перестає бути JSON, а «це не звіт» — кепський спосіб сказати «це
змінили». Не той ключ, змінене значення, дописаний байт і відсутній
файл підпису — кожен із них дає код виходу 4, той самий, що й зламана
хеш-сума, бо всі чотири — той самий провал: те, що тут лежить, не можна
показати як те, що було написане. Markdown-візуалізація не підписується:
вона — візуалізація, а R-03 — те, що дозволяє сумнівному зробити її
знову.*

## 5. `zvolfiles` — файли з файлових dataset-ів

### 5.1 Робота

Основний бінарник бачить файловий dataset щонайбільше як дамп об'єктів.
`zvolfiles` розуміє ZFS POSIX layer: каталоги, файли, симлінки, розширені
атрибути, власників і часові мітки — і витягає дерево каталогів або сирий
дамп об'єктів, коли метадані ZPL надто пошкоджені.

### 5.2 CLI

```
zvolfiles list     DATASET POOLSPEC [--txg N] [--key KEYSPEC] [PATH] [-R]
zvolfiles extract  DATASET POOLSPEC [--txg N] [--key KEYSPEC] [PATH...] -o DIR
                                    [--strict] [--preserve owner,times,xattr]
zvolfiles objects  DATASET POOLSPEC [--txg N] [--key KEYSPEC] -o DIR
```

### 5.3 Вимоги

| ID | Прі | Вимога |
|---|---|---|
| Z-01 | M | Читати master node ZPL, кореневий каталог і каталоги обох видів — micro-ZAP і fat-ZAP. |
| Z-02 | M | Декодувати system attributes (розкладка SA) для розміру, режиму, uid/gid, часів, кількості посилань; відкат на legacy-бонус `znode_phys`. |
| Z-03 | M | Звичайні файли, включно зі sparse-ділянками; симлінки (вбудовані в SA та об'єктні). |
| Z-04 | S | Розширені атрибути: на основі каталогів (`xattr=on`) і на основі SA (`xattr=sa`). |
| Z-05 | M | Маніфест `manifest.json` у вихідному каталозі: кожен витягнутий шлях із розміром, режимом, власником, часами, SHA-256 і кількістю помилок для цього файлу. |
| Z-06 | M | Нечитабельні блоки стають нулями з логуванням діапазону (ТЗ F-33); `--strict` натомість перериває. |
| Z-07 | S | Жорсткі посилання відновлюються як жорсткі посилання у вихідному каталозі, коли витягнуто обидва шляхи. |
| Z-08 | S | `objects` (ТЗ F-29): один файл на об'єкт плюс `objects.json` з метаданими dnode — запасний варіант, коли Z-01 не вдається. |
| Z-09 | S | Властивості dataset-у `casesensitivity`, `normalization` і `utf8only` враховуються при зіставленні `PATH`. |
| Z-10 | C | Великі dnode-и, project quotas та інші розширення розкладки SA через feature flags. |

### 5.4 Приймання

Fixture-файловий dataset із вкладеним деревом, sparse-файлами, симлінками,
xattr і жорсткими посиланнями, знищений після знімка його хешів:
`zvolfiles extract` на останньому доброму TXG відтворює дерево зі збіжними
хешами та метаданими; `objects` дає той самий вміст файлів, коли ZAP
кореневого каталогу навмисно занулено.

*Стан: Z-01…Z-03, Z-05, Z-06 і Z-08 реалізовані, а друга половина цього
приймання — крок у CI: дерево фікстури перелічується з режимами,
розмірами, часами й ціллю симлінка, взятими із системних атрибутів;
видобувається з маніфестом, який хешує кожен файл; і — коли ZAP
кореневого каталогу занулено на кожному члені — `list` падає, а `objects`
все одно дає `sub/deep.txt` побайтово.

Два свідомі відхилення від CLI вище. `PATH` — це `--path`, бо перелік
членів має змінну довжину і голий шлях після нього не відрізнити від ще
одного члена. І символьне посилання записується як файл із його ціллю, а
не як посилання: посилання з відновленого дерева вказувало б на те, що
лежить за цим шляхом на машині, де відновлюють.

Фікстура синтетична, і це справжнє обмеження, яке варто назвати: на
відміну від шляху для томів, цей код не ганяється на жодному пулі
`ztest`, бо ztest не робить заповнених ZPL-датасетів. Декодування пише й
читає той самий workspace, тож помилка порядку байтів в обох не
виявиться. `objects` і маніфест — те, на що спиралося б відновлення, поки
не спробувано справжню файлову систему; це записуватиметься в
[REALWORLD-TESTS.uk.md](REALWORLD-TESTS.uk.md).

Z-04, Z-07 і Z-09 реалізовані й покриті тим самим кроком. Розширені
атрибути читаються з обох місць, де вони живуть, — упаковані в системні
атрибути як nvlist (`xattr=sa`) і у власному прихованому каталозі
об'єкта (`xattr=on`), — і *записуються в маніфест зі своїми значеннями, а
не застосовуються*, бо встановлення атрибута потребує власного виклику
платформи, а цей workspace не лінкує системних бібліотек. Об'єкт,
зустрінутий під другим іменем, записується жорстким посиланням на перше,
а не копіюється, тож дерево зберігає ту форму, яку мало.

Ім'я — це байти, а не текст. Dataset із `utf8only=off` має право тримати
ім'я, яке взагалі не UTF-8: у Linux ім'я файлу — будь-який рядок байтів
без `/` і NUL, — а розкодування такого імені в символи заміни мовчки
перейменувало б файл, чого криміналістичне видобування робити не сміє.
Тож байти несуться від ZAP каталогу через обхід аж до виходу, і файл
виходить названим так, як він і звався. Те, що друкується й потрапляє в
JSON, лишається текстом, бо термінал іншого не вміє; поруч із ним
`path_hex` дає точні байти, і він присутній лише там, де друк щось
втратив. У фікстурі лежить `caf\xe9.txt` — `café.txt` так, як його
записала машина в Latin-1, — і CI перевіряє, що його видобуто саме під
цими байтами, знайдено саме за цими байтами і *не* знайдено за тим
текстом, у який він друкується, бо такого імені не має жоден файл.

Шлях зіставляється спершу за байтами, а зі згортанням регістру — лише
там, де про це каже `casesensitivity` dataset-а.

Не реалізовано: `normalization` при зіставленні шляхів (вона
повідомляється) і розширення SA-розкладки за feature-прапорцями
(Z-10). Sparse-ділянки виходять дірками, якими вони й є в дереві; файл,
чий хвіст ніколи не писався, видобувається на довжину, яку дають
атрибути.*

## 6. Поставка

Супутні інструменти йдуть за етапами ТЗ §10; жоден не виходить до
